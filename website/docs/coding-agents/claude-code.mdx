# Agent Collections in Claude Code

Claude Code reads the process rules from `CLAUDE.md` on every session. The Engineering Manager role delegates research, planning and code review to the role subagents (Context Engineer, Architect, Code Reviewer), so review runs in a separate context by default. Implementation is delegated with the `eversis-implement-common-task` prompt; it has no dedicated subagent file.

## The delivery cycle

Each stage shows what the process does and which Claude Code tools do the work. Quick Flow can skip Research and Plan.

### Tools at each stage

| Stage | Kind | Tool | Note |
| --- | --- | --- | --- |
| Ideate | Process | Agent Collections | Turns workshop materials into Jira-ready stories. |
| Ideate | Command | `/eversis-analyze-materials` | Optional. Starts from workshop materials. |
| Start | Process | Agent Collections | Prints the Implement readiness block and picks Quick or Full. |
| Start | Command | `/eversis-implement <ticket>` | A thin pointer in `.claude/commands/` to the prompt in `.ai/prompts/`. |

| Start | Rule | `.claude/rules/eversis-accessibility.md` | Loads for matching UI files. |

| Research | Skill | `.claude/skills/eversis-orchestrating-implementation` | — |
| Research | MCP | `eversis-collections`, `atlassian` | Skills, domain context and the ticket. |
| Plan | Process | Agent Collections | Writes `*.plan.md` with phases and acceptance checks. |
| Plan | Sub-agent | `eversis-architect` | Architect. Runs the `eversis-plan` prompt. |
| Plan | Skill | `.claude/skills/eversis-creating-implementation-plans` | — |
| Plan review | Process | Agent Collections | Checks the plan before you see it. Only a BLOCKER sends it back to Plan, at most three rounds. You approve the plan before Implement starts. |
| Plan review | Role | Plan Reviewer | Runs the `eversis-review-plan` prompt and writes `*.plan-review.md`. There is no generated sub-agent file for this role: the Engineering Manager delegates it. |
| Implement | Process | Agent Collections | Changes the code, then runs lint, typecheck and tests. |
| Implement | Role | Software Engineer | Runs the `eversis-implement-common-task` prompt. There is no generated sub-agent file for this role: the Engineering Manager delegates it. |
| Implement | Tools | file edits and terminal | — |

## What gets installed

| Path | What it holds |
| --- | --- |
| `CLAUDE.md` | One section for each of the six always-on rules |
| `.claude/rules/eversis-accessibility.md` | The accessibility rule, loaded for matching UI files |
| `.claude/commands/eversis-*.md` | Thin pointers to the prompts in `.ai/prompts/` |
| `.claude/skills/eversis-*/` | Skill packages, linked or copied by the installer |
| `.claude/agents/eversis-*.md` | The three role subagents — see [Role subagents](#role-subagents) |
| `.claude/hooks/eversis-validate-spec.cjs` | The spec artifact hook, run after file writes and around shell (Bash) commands — see [Spec artifact hook](#spec-artifact-hook) |
| `.claude/settings.json` | Two framework hook entries that run the hook: `PreToolUse` on `Bash` (before each shell command) and `PostToolUse` on `Write`, `Edit`, `MultiEdit` and `Bash` (after file writes and shell commands); your own settings and hooks are kept |
| `.mcp.json` | MCP servers, including `eversis-collections` |

These files are generated. Do not edit them by hand: the next sync overwrites them.

## Role subagents {#role-subagents}

A subagent is a separate Claude Code worker with its own context that the main session hands one job to. The framework installs three, so research, planning and review each start from the right instructions instead of from memory or an old file:

| Subagent | Stage | What it does |
| --- | --- | --- |
| `eversis-context-engineer` | Research | Reads the research prompt, skill and template, then writes or updates the research file |
| `eversis-architect` | Plan | Reads the plan prompt, skill and template, then writes or refreshes the implementation plan |
| `eversis-code-reviewer` | Review | Reads the review prompt and skill, then reports PASS / BLOCKER / SUGGESTION. It can read files and run checks, but has no edit tools and is read-only |

A subagent cannot talk to you. When it has a question, or needs a file change it is not allowed to make (such as the reviewer's row in the plan Changelog), it puts that in its final message, and the Engineering Manager (the main session) asks you or makes the change. Approval gates stay with the main session.

Cursor also reads `.claude/agents/`. The reviewer carries `readonly: true` for Cursor next to its Claude Code tool list.

## Spec artifact hook {#spec-artifact-hook}

A hook is a command Claude Code runs automatically before or after a tool call. The framework's hook, `eversis-validate-spec`, checks every research (`*.research.md`) and plan (`*.plan.md`) file under `docs/specs/` right after Claude writes or edits it, or changes it with a shell command, so a file that does not follow the framework template is caught before you are asked to approve it.

- It runs after `Write`, `Edit` and `MultiEdit`, including writes made by the subagents. Every other file is ignored.
- It also checks spec artifacts changed by shell (`Bash`) commands, such as `printf … >>`, `sed -i` or a script, including commands run by the subagents. Just before each shell command, a `PreToolUse` entry records when the command starts; after the command, the `PostToolUse` entry checks every research and plan file under `docs/specs/` changed since then.
- It compares the file with the framework's research or plan template: required sections, the `[CREATE]` / `[MODIFY]` / `[REUSE]` marker and the **Files** and **Definition of Done** parts of every task, and a Code Review phase at the end of a plan.
- The shell check looks at file modification times, so it also reports a research or plan file that changed for another reason while the command ran, for example after `git checkout` or `git pull`, or an edit made in parallel. Such a report lists real gaps in that file; it is not a false alarm about its content.
- A shell command that fails is not checked, because Claude Code does not run the after-command hook for it. Before a research or plan approval gate, the Engineering Manager runs the same check by hand when needed.

The installer writes these two entries into `.claude/settings.json`, both running the same command:

```json
"hooks": {
  "PostToolUse": [
    {
      "matcher": "Write|Edit|MultiEdit|Bash",
      "hooks": [{ "type": "command", "command": "node \"${CLAUDE_PROJECT_DIR}/.claude/hooks/eversis-validate-spec.cjs\"" }]
    }
  ],
  "PreToolUse": [
    {
      "matcher": "Bash",
      "hooks": [{ "type": "command", "command": "node \"${CLAUDE_PROJECT_DIR}/.claude/hooks/eversis-validate-spec.cjs\"" }]
    }
  ]
}
```

An older install has a single `PostToolUse` entry with the matcher `Write|Edit|MultiEdit`, which does not check shell commands. Run the installer with `--upgrade --sync` to get both entries; `--doctor` reports the missing one until then.

**What you see when a file fails.** The write or shell command has already happened. Claude Code shows the hook's output in the session, Claude fixes the file, and the hook runs again on the next write. The output lists each gap, for example:

```text
docs/specs/proj-123-context-management/proj-123-context-management.plan.md: 2 gaps
  - missing section: ## Human gates
  - last phase is not Code Review: ### Phase 3: Rollout (line 120)
A section missing from an existing file may be added with one line such as "No data — section added during DELTA <date>" instead of invented content; record it in a Changelog row.
```

As the last line says, an older file that lacks a section may get that one filler line plus a Changelog row, instead of invented content. If the hook cannot find the framework's checker, it says `validator not found at …` instead of passing silently.

**Node version.** The hook runs `node`, so it follows the [Node.js 22](../getting-started/installation.mdx#nodejs-22) rule: with Node older than 18 it reports that the check cannot run, and with Node 18–21 it still checks and adds an end-of-life warning.

**Windows.** Claude Code on Windows needs **Git Bash** for the hook — the same tool the installer already needs. Without Git Bash, Claude Code runs hook commands in PowerShell, where the hook's project path may not resolve.

To check that the hook is installed and working, run the installer's [`--doctor`](../getting-started/installation.mdx#doctor).
