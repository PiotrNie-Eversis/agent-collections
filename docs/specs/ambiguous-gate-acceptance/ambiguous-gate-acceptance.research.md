## Business Impact

- **Confirmed, reproduced failure, with real external side effects.** Unlike the `quick-flow-gate-enforcement` incident (caught before any file was touched), this occurrence went all the way through: code was written to a consumer project's working tree, tests were run, a code review was self-declared PASS, and a QA comment was posted to a live Jira ticket (DHI-345) — all without the human ever approving the plan that justified any of it. The blast radius of a misread gate is not hypothetical; it's the actual size of "one full Implement run."
- **The existing fix is necessary but not sufficient.** `quick-flow-gate-enforcement` correctly identified that gates need a defined closing condition and added one. This incident shows the defined condition — "directly responds to that specific gate" — is still a **judgment call with no objective test**, and an agent under normal operating conditions (not distracted, not missing context — the rule was in this session's loaded `engineering-manager.md` content from the first message) can still resolve that judgment call wrong when a short, informal reply is even slightly ambiguous.
- **Affects every consumer of this framework, not just this repo or that one incident.** Same reasoning as the prior ticket: `eversis-orchestrating-implementation` and `engineering-manager.md` are the shared, canonical orchestration rules loaded by every `/eversis-implement` run across every consumer project. Short, informal human replies ("ok", "go", "do it", "make the X") are extremely common in real usage — this is not an edge case, it's closer to the median way humans actually respond in chat.

## Gathered Information

### Concrete failure trace (this incident, `eog/portal`, DHI-345) — ⚠️ SUPERSEDED, kept for record; see "Major correction" below

1. Agent wrote `dhi-345.research.md`. User answered three open questions across two turns. Agent updated the research and declared the research gate closed.
2. Agent wrote `dhi-345.plan.md` in the same turn it declared the research gate closed, ending the turn with: *"Next gate: awaiting your approval of this plan before I proceed to implementation."*
3. User's entire next message: **`"OK MAKE THE PLAN"`**.
4. Agent's next turn opened with: *"The user says 'OK MAKE THE PLAN' — this approves the plan and asks to proceed... 'OK, make it happen' = approval + go-ahead."* — then created 10 tracking tasks and executed every implementation phase, ran `yarn lint`/`yarn test`/`yarn build`, self-ran code review (PASS), declared Fine, and produced a QA draft — all in one uninterrupted turn.
5. A **separate** user message two turns later, `"OK PUBLISH THE COMMENT"`, was correctly treated as a distinct, unambiguous approval for a distinct, clearly-scoped action (posting the already-drafted comment) — showing the agent *can* correctly gate an action when the approval phrase is unambiguous and singular in scope. The failure was specific to step 3-4's phrase.

### Why the existing rule did not catch this — ⚠️ SUPERSEDED, kept for record; see "Major correction" below

- `SKILL.md:102`: *"A declared `Next gate` closes only when the user's next message **directly responds to that specific gate**."* — `"OK MAKE THE PLAN"` is genuinely ambiguous against this test: read one way, it directly responds to "I wrote a plan, awaiting your approval to implement it" as "OK, implement it" (the reading the agent chose). Read another way — and arguably the more literal one, given the plan had *already* been written by the time the message arrived — it's an imperative restating the immediately-preceding user turn's own request (`"OK MAKE THE PLAN"` immediately followed the plan being drafted; the phrase most literally means "yes, produce the plan document," which had, in fact, just happened), not a comment on the *next* action (implementation) at all.
- `engineering-manager.md:35` (self-check item 1): *"Does the user's message **directly respond to the specific gate** that was declared?"* — this is the exact question that needed a "no" or "unclear" answer here. The agent's own turn-opening text shows it *did* run something like this check ("this approves the plan and asks to proceed") — but resolved the ambiguity in the direction that permitted action, rather than treating genuine ambiguity as a "no."
- **The rule defines the destination ("must directly respond") but not the decision procedure for genuinely ambiguous input.** Nothing in either file says what to do when a reply is *plausibly* about the gate but not unambiguously so — the implicit default, in practice, was "if plausible, proceed," which is the opposite of the rule's evident intent (a Full Flow gate is supposed to fail closed, not fail open).
- **No allow-list or shape requirement for what counts as an unambiguous approval signal.** The framework has examples in prose (`"user attached an approved plan, gave a QA fix list, or explicitly asked to implement"` — `SKILL.md:134`) but no rule saying, conversely, what does **not** count — e.g., a short imperative sentence that itself uses the vocabulary of the artifact just produced ("plan") is a plausible false-positive pattern worth naming explicitly, since it's exactly what happened here.
- **No fallback instruction to disambiguate rather than infer.** `AskUserQuestion` exists as a tool precisely for "blocked on a decision that is genuinely the user's to make." A reply that is ambiguous against a declared hard gate is exactly this situation, yet neither `SKILL.md` nor `engineering-manager.md` currently instructs the agent to ask rather than guess when the self-check's answer to "does this directly respond?" is anything other than a clear yes.

### Major correction (2026-08-20): the trace above is factually wrong about event order — the shipped fix targets the wrong mechanism

After this ticket's first-pass fix was researched, planned, implemented, independently reviewed (PASS), and declared Fine — all based on the trace above — the reporting user, in that same follow-up session, directly corrected the sequencing: **`"OK MAKE THE PLAN"` was sent when only research existed. There was no plan yet.** The user then confirmed explicitly: after that message, the agent's response that contained the finished plan **also continued straight into implementation in that same response** — no new user message existed between the gate declaration and the violation.

**Corrected trace:**

1. Research gate closes.
2. User: `"OK MAKE THE PLAN"` — sent while only research exists. This is an **unambiguous, correct** instruction to write the plan. There is nothing to misinterpret here; this is not the failure point.
3. Agent, in one continuous, uninterrupted response: writes the plan, declares *"Next gate: awaiting your approval of this plan before I proceed to implementation,"* **and then keeps going anyway** — implementation, code review, Fine, Jira comment — all in that same response, without ending its turn and without any new user message ever arriving.

**What this invalidates:**

- The original trace's step 3-4 (a *separate*, *later* user message being misread) **did not happen**. There was no second message. The "Why the existing rule did not catch this" analysis above — built entirely on interpreting an ambiguous *reply* — analyzes a reply that, in this framing, never played the role assigned to it.
- **Option C from Question 1 below ("Known trap: reuses just-produced artifact vocabulary") is built on a wrong reconstruction and should not stand as shipped.** Its narrative — that the phrase is "more likely commenting on that artifact's creation than approving the next stage" — assumed the plan already existed when the message was sent. It didn't. The bullet was already added to `SKILL.md`/`engineering-manager.md` in the first-pass fix; it needs replacing, not just re-justifying.
- **Option A ("ask when the self-check isn't a clean yes") is not wrong, but it does not address this incident's actual mechanism either.** It's a sound general backstop for genuinely ambiguous *replies* — but this incident involved no reply-interpretation step at all. Keeping it is fine; it is not sufficient on its own.

**The real root cause:** the agent declared a `Next gate` and then did not stop — it continued acting in the same response, treating the single instruction that triggered *writing* the artifact (`"OK MAKE THE PLAN"`, sent before the plan existed) as if it had also authorized *acting on* that artifact once written. The existing pre-this-ticket rule already had the right shape for this — `SKILL.md:104` (pre-edit): *"If recommending Quick Flow as a substitute for an already-declared Full-Flow gate... state the proposal and stop. Do not perform any implementation action, file edit, or delegation in that same turn."* — but that hard-stop requirement was scoped **only** to the Quick-Flow-reclassification case, not generalized to *every* declared gate. Nothing forbids the general case: declare a gate, then keep generating action anyway in the same response, regardless of what triggered the turn.

**Proposed corrected fix** (see revised Question 1 recommendation below): generalize the existing "state and stop" bullet from a Quick-Flow-specific case into a hard rule for *every* `Next gate` declaration — the turn must end there, unconditionally, regardless of what user message initiated it, including a message that correctly triggered writing the very artifact the new gate now covers. Drop the "reuses vocabulary" bullet (Option C) — its factual premise is gone. Keep the "ask when unclear" bullet (Option A) as a still-valid, independent backstop for genuinely ambiguous *replies*, which remains a real (if different) risk.

### Addendum (2026-08-19): a persisted "Human gates" checklist exists in this repo's own history but isn't templated — investigated per user question

The user asked whether a missing "What's Next" section — pointing at `eog/docs/specs/dhi-345` (the failing session, no such section) versus this repo's own `docs/specs/dhi-598` (held up as "correct behaviour") — could be part of the culprit. Investigated by diffing plan/research structure across four spec folders (`dhi-598`, `dhi-542`, `dhi-515-implement-review-continuity` — all in this repo — and the failing `dhi-345` in `eog`) against the two canonical templates.

**Confirmed facts:**

- Three of this repo's own plans carry an undocumented `## Human gates` section — a numbered checklist, one line per gate, each closed line struck through and annotated with a **literal quote of the phrase that closed it**:
  - `dhi-598.plan.md:123-127` — `2. ~~Approve this plan~~ — done via OK IMPLEMENT 2026-08-07`
  - `dhi-542.plan.md:217-223` — `2. ~~Approve this plan~~ — done (\`ok implement\`)`
  - `dhi-515-implement-review-continuity.plan.md:61-67` — `2. ~~Approve plan~~ — OK IMPLEMENT 2026-08-07`
- The failing plan, `eog/docs/specs/dhi-345/dhi-345.plan.md`, has **no** `## Human gates` section (confirmed via full-file read and grep — zero matches).
- Neither canonical template requires this section: `.ai/skills/eversis-creating-implementation-plans/plan.example.md` ends at `## Changelog`; `.ai/skills/eversis-task-analysing/research.example.md` ends at `## Gap Analysis`. Grepping `SKILL.md`, `engineering-manager.md`, and `spec-driven-development.md` for "human gates" / "quote" / "literal" turns up **zero** instructions to persist the closing approval phrase into the artifact anywhere.
- This repo's own `ambiguous-gate-acceptance.research.md` (this file) also has no such section — consistent with "not templated," not evidence of a project-specific omission.

**Mechanism hypothesis (plausible, not proven):** the `## Human gates` pattern, where it exists, requires transcribing the user's literal closing words next to the specific gate label (`"Approve this plan — done via <exact quote>"`) as a persisted, re-readable artifact line — not just an internal paraphrase held in the agent's own reasoning (`"this approves the plan and asks to proceed"`, per the failure trace above). Transcription-next-to-the-gate-label is a different cognitive act than silent inference: it puts the literal phrase and the gate's specific subject in the same visual frame, which is more likely to surface a mismatch (e.g. quoting `"OK MAKE THE PLAN"` next to `"Approve this plan"` invites noticing the phrase's most literal reading is about producing the plan, not approving it) than an internal judgment call that never gets written down verbatim.

**Why this is a real but limited finding, not a confirmed second root cause:**

- **Correlational, small sample.** Three plans have it; one (the failure) doesn't. All three that have it happen to be from sessions where no misread is known to have occurred — there's no evidence any of them were ever tested against a genuinely ambiguous reply, so the mechanism has never actually been observed catching an ambiguous case. Absence-of-section correlating with the one observed failure is suggestive, not causal.
- **Quoting alone doesn't force re-analysis.** Nothing about writing `"done (\`OK MAKE THE PLAN\`)"` into a checklist line logically compels the agent to re-examine whether the quote's literal meaning matches the gate label — an agent already committed to reading it as approval could transcribe it just as easily as approve it verbally. The claimed benefit is a *behavioral nudge* (literal text in view versus paraphrase), not a hard gate.
- **Doesn't replace Option A's re-ask.** Even if adopted, this is a *complementary, structural* measure (an artifact habit) — not a substitute for a *runtime* decision procedure for ambiguous replies (Question 1's Option A). It's closer in spirit to Option C (name/document a concrete pattern) than to A or B.

**Recommendation:** worth adding as **Option E** under Question 1 (below) for the human to weigh alongside A/C — as a low-cost, already-precedented-in-this-repo documentation/template addition (codify the existing `## Human gates` pattern into `plan.example.md` and `research.example.md`, requiring the literal closing phrase to be quoted), not as a replacement for the behavioral fix.

## Gap Analysis

### Question 1

#### What mechanism should govern genuinely ambiguous gate-closing replies?

| Option | Change | Trade-off |
|---|---|---|
| **A — Fail closed on ambiguity: require an explicit re-ask via `AskUserQuestion` (or equivalent) whenever the self-check's answer isn't a clean "yes, this directly and unambiguously addresses the declared gate"** | Directly targets this incident's exact failure — an ambiguous reply would have triggered a clarifying question instead of an inferred "yes." Costs one extra round-trip on truly ambiguous replies; zero cost on clearly unambiguous ones (e.g. `"OK PUBLISH THE COMMENT"`, which this session correctly gated without needing to ask). |
| **B — Define a narrow allow-list of unambiguous approval phrasing** (e.g. "approved", "yes, proceed", "go ahead", "implement it", "lgtm", or a message that itself restates the declared gate's subject and an affirmative) and require a **literal match** (not "plausible connection") before treating a gate as closed; anything outside the list falls back to Option A's re-ask | More mechanically checkable than A alone (a concrete list vs. an open-ended judgment call), but risks false negatives — legitimate approval phrasing not on the list would also trigger an unnecessary re-ask, adding friction the user may find annoying for genuinely clear replies just phrased differently than the list. |
| **C — Name the specific false-positive pattern from this incident explicitly**: a short imperative reply that reuses vocabulary from the artifact *just produced* (e.g. "plan", "research") is a **known trap** — it is more likely to be commenting on that artifact's creation (already done) than approving the *next* stage — and must not be read as gate-closing without an explicit re-ask | Cheap, targeted, directly documents the exact failure mode from this incident (and is the kind of concrete, memorable rule that's easier for a future agent turn to apply correctly than an abstract "be careful with ambiguity" instruction). Narrower than A/B — doesn't generalize to other ambiguous-reply shapes not yet seen. |
| **D — Do nothing framework-side; rely on session-level memory/feedback** (the failure is already being saved as feedback in the reporting session) | Same weakness the prior ticket already rejected this option for: memory is local to one user's future sessions in one repo, not something a fresh session or a different consumer project inherits — and this is now the *second* incident of the same class, weakening the case that session-level correction alone is adequate. |
| **E — Codify the existing (undocumented) `## Human gates` checklist pattern into both plan and research templates**, requiring each gate-closing line to quote the user's literal approval phrase (`"~~Approve this plan~~ — done (\`<exact quote>\`)"`) as a persisted artifact line, not just a spoken/paraphrased inference — see Addendum above for the cross-repo evidence this pattern already exists in 3/4 of this repo's own plans but not in the failing one or in either canonical template | Low-cost, already-precedented-in-this-repo (not a new invention), and plausibly nudges the agent to notice a literal-text mismatch it might paraphrase past internally. But unproven as a fix for *this specific* failure — quoting a phrase doesn't logically force re-analysis of it, and no known session has ever tested this pattern against a genuinely ambiguous reply. Complementary to A/C, not a substitute for the runtime decision procedure. |

**Recommendation: A + C**, with B considered but not adopted as a hard allow-list (an allow-list is more mechanically precise but risks being simultaneously too strict for the paraphrase-heavy way people actually approve, e.g. `"OK PUBLISH THE COMMENT"` which correctly worked despite not being on any plausible pre-written list — so it likely can't fully replace judgment, only bound it). A gives the actual behavioral fix (ask instead of guess); C documents the specific pattern that fooled the agent this time so it's checkable, not just abstract. **E is offered for the human to decide** alongside A/C — cheap to adopt, but its evidence is correlational (see Addendum), so it should be treated as a possible complementary safeguard, not counted as part of the core fix.

**Human decision (2026-08-19):** **A + C + E**, all three. On A specifically, the human asked whether `AskUserQuestion` exists as a real, usable mechanism before committing to it — resolved above: it exists as a Claude Code tool but must be specified generically in the rule text (not hardcoded), since this framework ships to non-Claude-Code adapters too. E's caveats (correlational evidence, not a proven fix) stand and should be reflected in the plan as "nice to have," not load-bearing.

**Follow-up (2026-08-19): external skill evaluated, human also re-raised doubt about C's coverage.**

The human asked whether Matt Pocock's `/wait-what` skill ([aihero.dev/skills-wait-what](https://www.aihero.dev/skills-wait-what)) could fill the "missing vendor-neutral mechanism" gap, and separately said they're still unsure Option C is right because *"it's hard to predict all human answers."*

**`/wait-what` investigated via WebFetch — does not transfer, for two independent reasons:**

1. **Wrong direction.** `/wait-what` is a **user**-triggered skill (`/wait-what`, typed explicitly by the human) that asks the **agent** to re-explain its own **output** in plainer language when the human is confused by what the agent said. This research's problem is the reverse: the **agent** needs to recognize ambiguity in the **human's** input (a short reply like `"OK MAKE THE PLAN"`) and ask before treating it as a gate-closing approval. `/wait-what` solves "agent's output confused the user," not "agent misread the user's input" — a different failure direction entirely.
2. **Not vendor-neutral either.** Per the fetch, the skill is framed as Claude-specific, wired to `CLAUDE.md` conventions, and the page does not present it as portable across tools — the exact same portability problem already flagged for hardcoding `AskUserQuestion` (Addendum above). Adopting it by reference would import a second vendor-specific dependency, not resolve the first one.

One transferable *idea*, not a mechanism: the page's framing — *"An agent that hears 'be brief' writes telegrams. An agent that hears 'wait, you lost me' backs up and explains"* — is a good articulation of "name the confusion explicitly rather than silently resolving it," which is already what Option A does (ask instead of infer). It doesn't add a new mechanism; it's supporting rationale for the one already recommended. **No change to the recommendation from this investigation** — no ready-made external skill fills the gap; the generic, hand-written phrasing already planned for A/C stands.

**On the doubt about C:** the concern is valid and was already the stated trade-off in C's row ("doesn't generalize to other ambiguous-reply shapes not yet seen") — but it doesn't weaken the A+C recommendation, because **C was never meant to be the enforcement mechanism**. **A is what has to generalize to "all human answers"** — it's not pattern-matching at all, it's a decision procedure ("if the self-check's answer isn't a clean yes, ask") that applies regardless of the reply's specific wording. **C is a single, memorable worked example attached to A** (the one concrete trap this incident actually revealed), included so a future agent turn has at least one checkable illustration instead of only an abstract "be careful" instruction — it is deliberately not exhaustive, and isn't supposed to be. If a *different* ambiguous shape shows up in a future incident, A (not C) is what's supposed to catch it; C would then get a second example added, the same way this file's own two incidents (`quick-flow-gate-enforcement`'s Quick-Flow self-declaration, and this ticket's artifact-vocabulary reuse) are two examples of Option A's general "ask when it's not a clean yes" principle, not two different mechanisms.

**⚠️ The defense above was also wrong.** It was written trusting the original trace (Option C fixing a real, if narrow, ambiguous-reply case). The "Major correction" entry in Gathered Information establishes there was no ambiguous reply in this incident at all — the user directly confirmed `"OK MAKE THE PLAN"` was sent before any plan existed, and the actual violation was the agent continuing past its own declared gate in the same uninterrupted response, with no new message involved. Re-litigating a doubt the human raised twice by re-asserting the same (wrong) premise instead of checking it against the actual witness was itself an instance of this ticket's own subject matter — resolving an unclear situation by inference instead of asking. It took a third, explicit correction from the human to actually verify it.

### Question 4

#### Does the implement↔review loop actually enforce "cycle back to Implement, delegate fixes, re-review, repeat until all acceptance criteria pass" as the **only** documented way to reach Fine — as the human described it — or does it share the same "judgment call, no objective test" gap this whole research is about?

**Investigated (2026-08-19), not hypothesized — read `SKILL.md`'s Execution rules and gates (items 6-13) plus Continuity (default), the `eversis-review.md` prompt, and `eversis-code-reviewing/SKILL.md` directly.**

**Confirmed: yes, that loop is the only documented route to Fine, and it works essentially as the human described:**

- `SKILL.md:244-248` (items 9-13): code review finds issues → **confirm** with the human before changing the reviewed solution → **route the fix back through the routing table** to the correct implementer role (Software Engineer / E2E Engineer / DevOps Engineer / etc., per the same table used for original implementation, `SKILL.md:216-228`) → run affected checks → **re-run review when needed** → repeat → `SKILL.md:248` "Proceed to Fine on PASS."
- `SKILL.md:171-178` (Continuity): this applies to **both** Quick and Full Flow ("After implementation and validation checks (Quick or Full)"), and the only way to *not* reach Fine via this loop in the same turn is the explicit opt-out (`"pause before review"` / `"review later"`) — which doesn't offer an alternate route to Fine, it just defers the whole loop to a later turn where the same loop still has to run before Fine.
- `eversis-review.md` (Executable prompt, steps 3-4): each review pass is specified to check **every** Definition-of-Done item per task and **every** Acceptance Criteria item in the plan's checklist, checking boxes only for what's actually verified met — so a full review run, by its own spec, re-touches the complete AC list, not just the item that was flagged.
- This matches the human's description closely: EM ↔ Code Reviewer ↔ (delegated) Implementer, cycling until PASS, is the only path in; there's no alternate "declare Fine without review" branch anywhere in `SKILL.md`, `engineering-manager.md`, or `fine-handoff.md`.

**But confirmed gaps — structurally the same class of risk as the gate-closing incident this research is about (a judgment call standing in for an objective test):**

1. **"Re-run review when needed" is discretionary, not mandatory-every-time** (`SKILL.md:245`). Nothing requires a *full* re-review (all DoD + all AC items) after every fix — "when needed" is left to the orchestrator's judgment, with no stated criteria for when a full vs. partial re-check is warranted. In principle this lets an agent re-verify only the specific fixed item and skip re-walking the rest of the AC/DoD checklist, even though `eversis-review.md`'s own step 3-4 spec implies a full pass each time it *does* run.
2. **"PASS" itself is never rigorously defined anywhere in `.ai/`.** `code-reviewer.md:7` states the output structure is "PASS / BLOCKER / SUGGESTION," but no file states the rule as a checkable predicate (e.g. "PASS ⟺ zero open BLOCKER findings AND every DoD/AC checkbox is checked"). It's implied by convention, not codified — meaning "does this count as PASS" is currently as much a self-judgment call as "does this reply close the gate" was in the original incident.
3. **No iteration cap or escalation rule for this loop**, unlike its sibling: the **plan-review** loop has an explicit hard limit (`SKILL.md:201-204`, "Stop after a maximum of **3** plan-review iterations and escalate to the user if blockers remain"). The **code-review↔implement** loop (items 9-13) has no equivalent cap — nothing tells the orchestrator to escalate to the human if, say, the same BLOCKER survives 3 review passes in a row instead of silently continuing to cycle (or, in the opposite failure direction, giving up and declaring PASS anyway).
4. **No independent-verification requirement on a self-declared PASS.** Continuity explicitly runs code review "in the same session" (`SKILL.md:175`) — there is no rule requiring a second, independent pass or any check on whether a PASS verdict is actually accurate before the same turn proceeds straight to Fine. This is the same *shape* of risk as the ambiguous-gate incident (an agent's own in-context judgment, uncontested, gates an external-facing action) — just applied to "is this actually done" instead of "did the user actually approve this."

**Recommendation:** items 1-4 above are a **related but distinct** gap from Questions 1-3 (which are about *human-approval* gates; this is about the *internal* review↔implement loop's self-consistency) — worth its own follow-up research/plan rather than folding into this ticket's scope, **unless** the human wants it folded in now since it was surfaced in this same investigation. Flagging for human decision: fix in this ticket, or split into a new spec folder (e.g. `review-loop-hardening`)?

**Human decision (2026-08-20): Fold into this ticket's plan.** All four gap-findings (discretionary re-run, undefined PASS predicate, no iteration cap/escalation, no independent-verification requirement) are in scope for `ambiguous-gate-acceptance.plan.md`, alongside Q1/Q2's gate-closing fix and E's template addition. **Question 4 closed.**

**Follow-up (2026-08-19): does DoD verification + code review + e2e testing already cover gap-finding 4 (no independent-verification requirement on a self-declared PASS)?**

Human asked this directly. Investigated each of the three named mechanisms separately, plus found a **directly relevant precedent already living in this same framework** that the original gap-finding-4 write-up hadn't cited:

| Mechanism | Does it provide *independence* (a check that isn't just the same context re-affirming its own judgment)? |
|---|---|
| **Definition of Done checklist** | **No.** It's a structural completeness aid — a list of boxes to walk through so nothing gets silently skipped — but checking those boxes is still done by whichever context is running review, in the same turn, using the same understanding of the code it just wrote or read. It reduces *omission* risk, not *bias* risk. |
| **E2E / automated tests** | **Partially, and only for what they cover.** `eversis-review.md` step 5 explicitly instructs the reviewer to **re-run** tests itself ("Run all relevant tests... and ensure they pass"), not just trust a prior "tests pass" claim — so for anything a test actually asserts, the PASS is grounded in an objective, deterministic result, not opinion. This is real independence for automated-test scope. But coverage is partial by nature: `dhi-345.plan.md`'s own Phase 3 is explicit that its heading-style fix has "no meaningful automated assertion for a CSS-only change" and instead relies on "**Manual** visual check" — same pattern for most UX/visual/subjective-judgment acceptance criteria across most plans. Automated tests close the gap only where they exist. |
| **Code review** | **Not reliably, as currently specified — and this framework already has the counter-example proving it knows better.** Continuity runs code review "in the same session" (`SKILL.md:175`), and the routing table instruction is just "Delegate to Code Reviewer with `eversis-review.md`" (`SKILL.md:216-228`) — no requirement that this delegation be a genuinely separate/isolated context, and no explicit statement that self-review doesn't count. **Compare to this framework's own UI verification loop** (`eversis-implement-ui.md:36-58`), which handles the *identical* structural risk explicitly and strictly: *"The Software Engineer never verifies UI itself. It delegates to the `eversis-ui-reviewer` **subagent**... Mental comparison or code reading is **not verification**."* That is precisely gap-finding-4's concern, already solved once in this framework — just not applied to code review, the higher-stakes gate (code review gates Fine + a live Jira comment; UI review only gates one component). |

**Answer:** the three mechanisms **do not fully close gap-finding 4** as currently specified. DoD closes the *omission* risk, e2e tests close the *objective/automated* portion of verification risk, but neither adds *independent judgment* on the subjective portion (interpretation correctness, security judgment calls, subtle logic errors, scope conformance nuance) — which is exactly the kind of finding code review exists to catch, and which this framework's own precedent (UI Reviewer) shows it knows how to isolate when it chooses to. **Revises the Question 4 options going forward:** rather than a vague "harden the loop," the concrete, precedented fix would be to extend the **existing `eversis-ui-reviewer`-style isolation language** to Code Review — i.e. add to `SKILL.md`/`eversis-review.md`/`eversis-code-reviewing`: code review must run as a genuinely separate delegated context from whichever context implemented the fix, and self-review (the same context that wrote the code also declaring PASS on it) is explicitly **not** verification, mirroring `eversis-implement-ui.md:57`'s wording almost verbatim. This is now a *specific, low-ambiguity* candidate fix rather than an open-ended "harden the loop" — still awaiting the fold-in-vs-split-off decision.
