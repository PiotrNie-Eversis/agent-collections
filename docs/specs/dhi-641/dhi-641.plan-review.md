## Top Failure Modes

- Phase 1 completes, `npm run build` passes green, everyone believes DHI-642 is done — then the next `npm run build` (or CI run, or `npm start`) silently regenerates `website/docs/prompts/**` back at its old top-level location via the `prebuild` hook, leaving a stale duplicate tree and an empty or half-populated `reference/prompts/`. This is the single most expensive rework trigger in the plan: it would surface late, look like an unrelated regression, and point at the wrong root cause.
- Phase 6 code review runs, `npm run build` is green, reviewer declares PASS — but `README.md`'s links to `./website/docs/workflow/overview.md`, `./website/docs/prompts/overview.md`, `./website/docs/agents/overview.md`, and `./website/docs/getting-started/migration-from-cursor-collections.md` are all 404s, because nothing in the plan's verification surface checks root Markdown. The "zero broken links" claim in Quality Assurance would be false at sign-off.

## Unproven Assumptions

- The plan assumes `npm run build`'s `onBrokenLinks: "throw"` is a complete safety net for "zero broken links" — it is only complete for links *inside* `website/`. Not verified against root `README.md`, `AGENTS.md`, or any other repo-level Markdown before this review.
- The plan assumes Task 1.1's Stop Rule ("if any external repo file links to old doc path... stop and list for follow-up") is a rare edge case. Codebase-reality check shows it is not an edge case — it is a certainty (README.md already has 4+ such links), so the plan should treat this as a normal task step, not an exceptional stop condition.

## Most Likely Rework Triggers

- Re-running Phase 1's file moves a second time after discovering the generator silently reverted `reference/prompts/`, once someone notices the docs site is regenerating content in two places.
- A follow-up ticket to fix README.md links after Phase 6 sign-off, once someone external clicks through from the README and hits a 404 — undermining the epic's own "reduce evaluator drop-off" goal from the outside in, the exact failure mode the source report was about.

## Questions the Architect Must Answer Before Coding

- Does updating `adapters/website/generate-prompts.mjs`'s two hardcoded path constants (lines 166, 237) count as "repo documentation" work in scope for the Repo Docs Writer, or does it need Software Engineer routing since it's a `.mjs` script, not a `.md` file?
- Should root `README.md`'s doc links be updated in Phase 1 (same task, since it's the same set of moved paths) or as a dedicated task at the end of the plan (safer against intermediate broken-link windows, but risks being forgotten if Phase 1's file-move task is marked "done" before README is touched)?

## BLOCKERS

### B1: Prompts generator hardcodes the pre-move output path and runs automatically before every build

`adapters/website/generate-prompts.mjs:166` (`path.join(outRoot, "website", "docs", "prompts", prompt.bucket)`) and `:237` (`path.join(outRoot, "website", "docs", "prompts")`) hardcode `website/docs/prompts/` as the generator's write target. `website/package.json`'s `prebuild` script (`npm run sync-changelog && npm run sync-docs`) runs this generator automatically before every `npm run build` — the exact command this plan uses as its verification gate in all 6 phases. Task 1.1 moves `prompts/` to `reference/prompts/` but never updates the generator, and the plan's own Wildly Important Goal explicitly lists the generator as "Do NOT touch." Net effect: the very first `npm run build` after Task 1.1 regenerates a fresh `website/docs/prompts/**` tree at the old location before compiling, either resurrecting the old sidebar entry or producing duplicate/conflicting content — the move does not actually hold. **Action needed:** revise Task 1.1 (or add a dedicated task) to update the two hardcoded path segments in `generate-prompts.mjs` to `website/docs/reference/prompts/`, and drop or narrow the "Do NOT touch" exclusion for this specific file. Also check `adapters/website/generate.mjs`'s own `--check` drift-comparison logic (lines ~100-117), which compares against the same hardcoded `website/docs/prompts/` path.

## WARNINGS

### W1: `check-skills.mjs` also hardcodes the pre-move `skills/` path

`adapters/website/check-skills.mjs` matches skill IDs against `website/docs/skills/*.md` and reads a "N reusable skills" count out of `website/docs/skills/overview.md` (confirmed via grep, lines ~7-8, ~98). This runs as part of `npm run sync:website-docs` (same `generate.mjs` orchestrator as B1) but is explicitly informational/non-blocking per that script's own `--help` text, so it will not fail the build — it will just silently report incorrect "missing skill" warnings once `skills/` moves to `reference/skills/`. Lower severity than B1 because it cannot break `npm run build`, but it is a second hardcoded-path instance the same root cause (Phase 1 moving folders that other scripts assume are top-level) produces, and it should be fixed in the same pass as B1 rather than discovered separately later.

### W2: Root `README.md` links are outside the plan's only verification surface

README.md (root) contains confirmed links to `./website/docs/workflow/overview.md`, `./website/docs/prompts/overview.md`, `./website/docs/agents/overview.md`, and `./website/docs/getting-started/migration-from-cursor-collections.md` (lines 101, 209, 229, 195/408) — all four move under this plan. `docusaurus.config.ts`'s `onBrokenLinks: "throw"` only validates links Docusaurus itself compiles (content under `website/`), so `npm run build` passing green gives no information about README.md's link health. The plan's Wildly Important Goal Success Measure ("zero broken internal links after the full move") is therefore not actually verified end-to-end by the stated check. **Action needed:** either add README.md path updates as an explicit task with its own deterministic DoD check (e.g. `grep` for the old paths returning zero matches), or narrow the Success Measure to state its actual scope ("zero broken links *within the Docusaurus build*") and track README.md as a separate, explicit task rather than an implicit Stop-Rule edge case.

## SUGGESTIONS

### S1: `use-cases.md` and `domain-context.md` cluster placement are Architect judgment calls, not sourced from the BA epic description

The BA's epic description (`extracted-tasks.md`) names "Agents, Prompts, Skills, Integrations" explicitly for the Reference cluster and "isolation, migration, for-CTOs" for Advanced — it does not mention `use-cases.md` or `domain-context.md` at all. The plan places `use-cases.md` under `main-flow/` and `domain-context.md` under `reference/`, which are reasonable calls, but they are new placement decisions made during planning, same category as the Team Guides decision the plan already surfaces as a resolved Open Question. Consider adding these two as explicit rows in the Open Questions table (marked Resolved with the same reasoning already implicit in the folder tree) so the Changelog trail is complete, rather than leaving them undocumented inside the Proposed Solution tree only.

### S2: Task 1.1's single end-of-task build check depends on moving the whole `reference/` cluster atomically

`agents/`, `prompts/`, `skills/`, and `integrations/` cross-link each other via relative paths (e.g. `agents/overview.md` → `../prompts/public/analyze-materials`). These only continue resolving because all four move together to the same new parent (`reference/`), preserving their relative depth to each other. The plan's single `npm run build` check at the end of Task 1.1 is structurally correct for this (no intermediate checkpoint to fail on), but the task Description doesn't say this explicitly — worth a one-line note so whoever executes it doesn't split the folder moves across separate commits with a build check in between, which would show spurious broken-link failures on a task that is actually fine once complete.
