## Wildly Important Goal

**Goal**: A first-time reader of `website/docs/` can find the page relevant to their current goal, and complete a first successful install, without first learning the framework's internal taxonomy (SSOT, adapters, MCP) or reconciling divergent instructions.

**Success Measure**: The top-level sidebar shows 4 intent-based clusters instead of 13 artifact-type sections, exactly one installation sequence exists site-wide, `cd website && npm run build` succeeds with zero broken internal links *within the Docusaurus build*, and a `grep` for old top-level doc paths across root `README.md` and `adapters/website/*.mjs` returns zero matches (the two surfaces `onBrokenLinks` cannot see — see Plan Review B1/W2).

**Do NOT touch / do NOT add**: Marketing homepage components' internal logic beyond importing/reusing them (`src/components/*`); the AI Hero site; visual/graphic redesign (colors, illustrations, branding — this is IA and content-ordering only, per the source report); `.ai/prompts/**` SSOT content or the *content-generation logic* of `adapters/website/generate-prompts.mjs` (Prompts Overview stays generated, not hand-edited — see Current Implementation Analysis); any application code beyond the specific hardcoded-path constants identified in Plan Review B1/W1 (`generate-prompts.mjs`, `generate.mjs`, `check-skills.mjs` — path segments only, not generation logic).

## Proposed Solution

Four new top-level Docusaurus folders replace the current 13 artifact-type sections, built by moving existing files (not rewriting them) into a new tree, then layering the content-density and onboarding-consolidation fixes on top of the new structure so file moves don't happen twice:

```text
website/docs/
├── intro.md                    (unchanged location — site root, slug: /)
├── getting-started/            (unchanged — minus migration-from-cursor-collections.md)
├── main-flow/                  (NEW cluster — day-to-day loop)
│   ├── workflow/               (moved as-is)
│   ├── team-guides/            (moved as-is — deferred-placement decision resolved here)
│   └── use-cases.md            (moved)
├── reference/                  (NEW cluster — "what is X" lookup)
│   ├── agents/                 (moved as-is)
│   ├── prompts/                (moved as-is — generated file inside untouched)
│   ├── skills/                 (moved as-is)
│   ├── integrations/           (moved as-is)
│   ├── domain-context.md       (moved)
│   ├── framework-reference.md  (moved + restructured)
│   └── glossary.md             (NEW)
└── advanced/                   (NEW cluster — CTO / enterprise topics)
    ├── for-ctos.md              (moved)
    ├── isolation.md             (moved)
    └── migration-from-cursor-collections.md (moved from getting-started/)
```

Docusaurus resolves the sidebar automatically from folder structure (`sidebars.ts` uses a single `autogenerated` tree — no manual sidebar array to edit), and `docusaurus.config.ts` has `onBrokenLinks: "throw"`, so `npm run build` is a hard, automated gate against broken cross-references after every move — this is the primary verification tool through the whole plan, not just a nice-to-have.

Because moving ~90 files (agents/skills/prompts/integrations subtrees) happens once in Phase 1, every later phase edits files **at their final path**, avoiding a second round of link updates.

## Technical Context

### Project Instructions

- `.ai/rules/orchestration/agent-core.md`, `testing-and-terminal.md` — run lint/typecheck/tests after non-trivial changes; discover commands from the repo (not assumed)
- Routing table (`eversis-orchestrating-implementation` SKILL.md) — "repo documentation" tasks (README, CHANGELOG, `docs/`, `website/docs`) route to **Repo Docs Writer** via `eversis-repo-docs-writer.md` — every implementation task in this plan is that task type; no Software Engineer delegation needed since no new component logic is written, only MDX composition and existing-component reuse

### Architecture & Patterns

- Docusaurus 3.10.2, single `autogenerated` sidebar tree keyed on `dirName: '.'` (`website/sidebars.ts`) — folder structure **is** the sidebar; no manual sidebar array to maintain
- Each top-level (and nested) folder carries a `_category_.json` (`label`, `position`, `collapsible`) controlling its sidebar entry
- `.md` files under `website/docs/` already support MDX-style JSX imports (confirmed working pattern: `docs/workflow/overview.md:96` imports `SdlcDiagram` directly) — no `.mdx` extension migration needed
- `website/docs/prompts/**` is **generated**, not hand-authored — footer comment: `<!-- GENERATED by adapters/website/generate-prompts.mjs from .ai/prompts/ — do not edit; run npm run sync:website-docs -->`. `website/docs/agents/**` and `website/docs/skills/**` are hand-authored (no such footer)

### Tech Stack

- Node.js, npm workspaces-style per-package scripts (no root lockfile-driven monorepo tool beyond plain npm)
- `website/package.json`: `@docusaurus/core` 3.10.2, `@docusaurus/preset-classic`, `@docusaurus/theme-mermaid`, `@easyops-cn/docusaurus-search-local`, React 19.2.6
- No test runner configured for `website/` (no `test` script) — `docusaurus build` (which runs full MDX compilation, sidebar generation, and link resolution) is the correct and only automated verification surface for this epic

### Code Style & Standards

- Frontmatter conventions per existing files: `sidebar_position`, `title`, sometimes `slug`, `id`, `description` — follow the pattern of the file being moved/edited, do not invent new frontmatter keys
- Admonition syntax already used site-wide: `:::info Start here`, `:::tip`, `:::brand`, `:::note` — reuse existing admonition types rather than introducing new ones

### Testing Patterns

- Primary check (every task in this plan): `cd website && npm run build` — fails the build (`onBrokenLinks: "throw"` in `website/docusaurus.config.ts:15`) on any broken internal link, which is exactly the risk DHI-642's redirect requirement guards against
- Secondary check where a task touches `website/docs/prompts/**` indirectly: `npm run sync:website-docs:check` (root `package.json`) — confirms no drift between `.ai/prompts/` SSOT and the generated pages; used only to **verify** Question 3's finding, not to make changes

### Database Patterns

Not applicable — static documentation site, no database.

### Additional Context

- No Figma involvement anywhere in this epic — pure content/IA work, so no `[REUSE]` UI Reviewer verification tasks are included per the plan-content rules
- `getting-started/migration-from-cursor-collections.md` moves to `advanced/` per the BA's own epic description ("Advanced/CTO: isolation, migration, for-CTOs") even though DHI-642's Jira description doesn't name it explicitly — flagged in Changelog as a plan-time scope clarification, not a deviation
