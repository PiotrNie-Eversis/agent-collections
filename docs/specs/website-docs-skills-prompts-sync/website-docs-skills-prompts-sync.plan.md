## Proposed Solution

Kolejność faz zaprojektowana pod maksymalną dźwignię: najpierw zbudować generator promptów (Faza 1-2), bo eliminuje ręczną naprawę **29 z 73** plików mechanicznie (regeneracja z już poprawnego `.ai/prompts/**`) zamiast edytować każdy z osobna. Po drodze generator ujawnia dwa błędy, które żyją w samym `.ai/` źródle, nie w kopii — naprawić je od razu (Faza 3), bo inaczej regeneracja wiernie odtworzy błędną treść. Skille (Faza 4-5) nie da się w pełni wygenerować — `SKILL.md` to treść proceduralna dla agenta, strona `skills/*.md` to kurowane streszczenie dla człowieka (różna treść, nie transformacja 1:1, zweryfikowane porównaniem `eversis-creating-prompts/SKILL.md` [244 linie] vs `skills/creating-prompts.md` [34 linie]) — więc 43 strony wymagają ręcznej naprawy P1-P5 + drift-check (nie pełna generacja) pilnujący tylko istnienia/liczby, nie treści.

## Technical Context

### Project Instructions

- `.ai/rules/orchestration/agent-core.md` — hard limits: brak edycji poza zakresem bez zgody, brak cichego skracania komentarzy dokumentacyjnych, brak nowych zależności npm.
- `.ai/skills/eversis-writing-repo-documentation/SKILL.md` — "Writing for a Mixed Audience" (5 zasad czytelności) obowiązuje na każdej ręcznie edytowanej stronie (43 skille + 5 nowych); nie dotyczy generowanych stron `prompts/**` (treść dziedziczona z `.ai/prompts/**`, już przeszła przez ten sam standard u źródła).
- `.ai/skills/eversis-creating-skills/SKILL.md` — konwencja frontmatter `SKILL.md` (`name`, `description`, `user-invokable`) — potwierdza brak `title`/`slug`/`sidebar_position`/kategorii w źródle, stąd decyzja "check, nie generate" dla skilli (patrz Proposed Solution).

### Architecture & Patterns

- Adapter = `generate*.mjs` (zero zależności npm, `fs`/`path`/`node:child_process` tylko) + opcjonalny `rule-map.yaml`/`skill-map.yaml` (constrained parser, wzorzec `adapters/cursor/rule-map.yaml` — **reużyć** istniejący `parseRuleMapYaml`/`loadRuleMap` z `adapters/sync.mjs` jeśli eksportowalny, albo skopiować wzorzec 1:1 zamiast pisać nowy parser od zera).
- `--check` = generuj do `fs.mkdtempSync(os.tmpdir())`, porównaj `normalizeNewlines` bajt-po-bajcie z docelowym katalogiem, zwróć listę dryftów, exit 1 — identyczny wzorzec jak `adapters/sync.mjs::runCheck`.
- Docusaurus: frontmatter YAML, `sidebar_position` steruje kolejnością (autogenerated sidebar, `dirName: '.'`), zero edycji `sidebars.ts`.

### Tech Stack

- Node.js (`.mjs`, ESM, zero zależności — zgodnie z `adapters/sync.mjs` nagłówkiem "Zero npm dependencies").
- Build weryfikacyjny: `npm run website:build` (`onBrokenLinks: "throw"`).
- Brak frameworka testowego dla `adapters/` — weryfikacja przez `--check` w CI-stylu (ręczne uruchomienie), wzorzec `sync:adapters:check` (dziś też bez wpiętego workflow CI — nie wynajdywać nowej infrastruktury CI w tym Planie, tylko dodać analogiczny skrypt npm).

### Code Style & Standards

- Generator = czysta funkcja read→transform→write, bez side-effectów poza `fs`, żadnych zależności zewnętrznych (zgodność z istniejącymi adapterami).
- Ręczne poprawki 43 stron skilli: mirror struktury sąsiednich stron (`eversis-writing-repo-documentation/SKILL.md`, "Structure mirrors neighbors"), gloss żargonu inline przy pierwszym użyciu na stronie.
- Weryfikować każdą liczbę (skille, prompty) wprost względem stanu repo w chwili Implement, nie kopiować z Research/Planu bez potwierdzenia (mogły się zmienić między Planem a Implement).

### Testing Patterns

- Po Fazie 1-2: `node adapters/website/generate.mjs --check` musi przejść (exit 0) po `node adapters/website/generate.mjs` (write) — round-trip test.
- Po każdej fazie dotykającej `website/docs/`: `npm run website:build` (zero broken links).
- Sweep końcowy: `grep -rniE '\.cursor/(skills|prompts)/|Cursor \(Chat or Agent\)' website/docs/skills website/docs/prompts` → zero trafień.
- `grep -rn 'specifications/<task-name>/\|specifications/' .ai/prompts/internal/*.md` → każde trafienie ma towarzyszące `docs/specs/` w tym samym pliku (Q5 systematic check, acceptance).
