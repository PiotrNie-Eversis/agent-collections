### Lifecycle model (canonical)

```text
Ideate
  └─ Research  → human gate
  └─ Plan      → human gate (+ optional plan-review)
Implement      → code + checks
Review         → eversis-review; blockers cleared
Fine           → QA draft (eversis-fine-handoff); post only with human OK
```

Quick Flow may SKIP research/plan **only** after adequacy checklist pass (already encoded in skill).

This story follows full spec-driven development (mandatory under epic DHI-515 / Agent Collections).

### Question 1 — detail (for decision)

**What must land somewhere (AC #1):** vendor-neutral documentation that the delivery lifecycle is Ideate → **Research** → **Plan** → Implement → Review, with human gates, required artifacts under `docs/specs/<issue-kebab>/`, and no implement without approved research/plan (when Full Flow / SDD applies).

**What `agent-core.md` already has today:**
- Plain-language lifecycle with only **three** top-level stages: Ideate → Implement → Review (Research/Plan are **buried** inside the Implement orchestration list).
- Human gates for research/plan approval and Fine.
- Orchestration steps 1–5 that already name Research, Plan, Implement, Review, QA draft.
- Skills discovery, quality bar, hard limits (~60 lines total).

So the **content** is mostly there; the **gap** is visibility and “this is the mandatory Delivery Standard,” not inventing a new process.

| Option | What we would do | Pros | Cons |
|--------|------------------|------|------|
| **A — expand `agent-core.md` only** | Rename/expand Lifecycle to five stages (or Ideate with Research/Plan explicit); add a short **Mandatory spec-driven development** section (folder naming, artifacts, gates, Fine); keep EM/skill as pointers | One always-on file; adapters/consumers always load SDD with agent-core; no new file to map in README/stack | File grows; mixes “who you are / hard limits” with “delivery process contract”; harder to attach SDD alone in some tools |
| **B — new `spec-driven-development.md` + pointer** | Keep agent-core lifecycle short but fix stage names + 2–3 sentence pointer; put full SDD contract (artifacts, Delivery Standard text, gitignore note, Fine) in dedicated rule | Clear separation: identity/limits vs delivery contract; easier to cite “load SDD rule”; thinner agent-core | Second file to discover; must ensure it is actually loaded (pointer + orchestration README + AGENTS/README) |
| **C — thin agent-core + EM owns depth** | agent-core only renames lifecycle; **`engineering-manager.md`** holds SDD depth | Keeps agent-core smallest | SDD only strong when EM/Implement runs — weaker for “always-on core rules” AC wording; Review-only sessions may miss SDD |

**Practical recommendation after detail:** Prefer **B** if you want a citable “Delivery Standard” artifact next to `fine-handoff.md`; prefer **A** if you want zero new rule files and accept a longer `agent-core.md`. **Avoid C** for AC #1 (“core orchestration rules”).

### Question 4
#### Soften Cursor `@` in Delivery Standard template text?
**Answer (approved):** **A** — stable ids (`eversis-implement`, `eversis-review`) + optional Cursor attach note.

**What the optional Cursor attach note is:**
In Cursor Chat/Agent, users often load a prompt by typing `@` and picking a file (e.g. `@eversis-implement` when the prompt is on the `@` path). That is **Cursor UX**, not the framework SSOT.

Under **Q4 A**, the Delivery Standard / template says the primary entry is the **stable prompt id** (load `eversis-implement` by reading `.ai/prompts/public/eversis-implement.md`, MCP, or tool-native attach). Then **one short optional sentence**, for example:

> *Optional (Cursor):* you may also attach the same prompt with `@eversis-implement` / `@eversis-review` if your project surfaces those files in Cursor.

That sentence is the “optional Cursor attach note”: it documents a convenience for Cursor users without making `@` the required or only way to start the workflow. Existing Jira tickets that already say `@eversis-*` are left as-is (Q2 = A, no retro-edit).
