## 1. Cel i zakres

Zbudować sekcję `/docs/team-guides/` z 6 podstronami rolowymi + landing, każda w identycznym szkielecie how-to (Hero/TL;DR → Quick Start → tabela scenariuszy → diagram Mermaid + tabela handoffów → ściągawka poleceń → Next steps), zarejestrowaną w nawigacji Docusaurus. Priorytet: UX/czytelność > kompletność, limit 500-600 słów treści właściwej na stronę.

**Twardy wymóg zadania:** zero fabrykowanych poleceń/agentów/skilli — wszystko musi być zweryfikowane w repo. Jeśli dla roli brakuje dedykowanego promptu, jawnie to zaznaczyć.

## 2. Stan repo — fakty potwierdzone

### 2.1 Framework dokumentacji

- **Docusaurus** (`website/`, `@docusaurus/theme-mermaid@3.10.2`), zbudowany lokalnie (`cd website && npm run build`).
- Mermaid **już skonfigurowany**: `docusaurus.config.ts` ma `markdown.mermaid: true` i `themes: ["@docusaurus/theme-mermaid"]` — nie trzeba dodawać żadnej konfiguracji.
- `.md` pliki w tym repo **wspierają importy JSX** (MDX) — potwierdzone w `website/docs/workflow/overview.md:96` (`import SdlcDiagram from '@site/src/components/SdlcDiagram';` wewnątrz pliku `.md`), więc nie trzeba przechodzić na `.mdx`, jeśli treść nie wymaga komponentu.
- Nawigacja: `sidebars.ts` używa **jednego** `autogenerated` drzewa z `dirName: '.'` — nowe foldery/pliki pod `website/docs/` pojawiają się w sidebarze automatycznie; **rejestracja sekcji = dodanie folderu `website/docs/team-guides/` + plik `_category_.json`** (nie trzeba edytować `sidebars.ts`).
- Konwencja `_category_.json` na istniejących sekcjach najwyższego poziomu (`{label, position, collapsible}`):

  | Sekcja | `position` |
  |---|---|
  | Getting Started | 2 |
  | Workflow | 3 |
  | Agents | 4 |
  | Prompts | 5 |
  | Skills | 6 |
  | Integrations | 7 |

  **Brak** sekcji o nazwie "Lifecycle" lub "Migration" na najwyższym poziomie (instrukcja zadania błędnie zakłada ich istnienie jako precedens) — "Lifecycle" to nagłówek wewnątrz `intro.md`, "Migration" to podstrona `getting-started/migration-from-cursor-collections.md`.

  **Umiejscowienie (decyzja użytkownika, 2026-08-27):** sekcja `Team Guides` ma znaleźć się **między Workflow (3) a Agents (4)**. Docusaurus `position` w `_category_.json` akceptuje wartości niecałkowite, więc rekomendacja: **`position: 3.5`** — wstawia sekcję we właściwym miejscu bez renumeracji `Agents`/`Prompts`/`Skills`/`Integrations` (renumeracja tknęłaby 4 pliki `_category_.json` spoza zakresu tego zadania, sprzeczne z twardym limitem "no edits outside task scope without approval").

- Brak dedykowanego komponentu "card grid" możliwego do importu w treści `docs/` — `HomepageFeatures` (`website/src/components/HomepageFeatures/`) jest zbudowany wyłącznie pod stronę główną (`styles.module.css` dopasowany do hero), nie jest używany nigdzie w `docs/`. Żadna istniejąca strona `docs/` nie importuje go do siatki kart. Rekomendacja: landing `team-guides/index.md` powinien użyć zwykłej tabeli/listy Markdown (rola, 1 zdanie, link) zamiast nowego komponentu React — spójne z resztą `docs/` i tańsze do utrzymania. Decyzja ostateczna należy do Planu.
- Brak istniejącego "wybornika ról" (tabs/cards) współdzielonego między stronami — jeśli Plan chce go na górze każdej podstrony, najprostsza opcja bez nowego komponentu to statyczna lista linków (Markdown) powtórzona na każdej stronie; Docusaurus ma wbudowany `@theme/Tabs` dostępny w MDX bez dodatkowych zależności, jeśli Plan wybierze wariant "tabs".

## 3. Luka: brak dedykowanej roli "Project Manager"

Zgodnie z `website/docs/agents/overview.md` (12 ról + 3 internal workers) **nie istnieje** rola/prompt/skill dedykowany PM. Najbliższy odpowiednik to **Engineering Manager** — ale to rola *orkiestrująca agentów* (`/eversis-implement`), a nie interfejs dla człowieka-PM.

Zgodnie z jawną instrukcją zadania ("NIE twórz treści na siłę — zgłoś to jako lukę i zaproponuj, gdzie framework już pomaga tej roli pośrednio"), rekomendacja dla podstrony PM (do potwierdzenia w Planie):

- Otwarcie strony wprost nazywa lukę: brak dedykowanego `/eversis-*` dla PM.
- Punkt styku PM z frameworkiem to **ludzkie bramki (human gates)** — zatwierdzanie `*.research.md` i `*.plan.md` przed Implementacją (`.ai/rules/orchestration/agent-core.md`), oraz czytanie **Draft QA comment** przy Fine (`.ai/rules/orchestration/fine-handoff.md`, skill `eversis-fine-handoff`) przed publikacją do Jiry.
- Artefakty, które PM czyta/zatwierdza, a nie generuje sam: `*.plan.md` (Architect), `*.plan-review.md` (Plan Reviewer), QA comment draft (Engineering Manager @ Fine).
- Quick Start dla tej strony nie może być "jedna gotowa komenda" w sensie promptu — musi być przeformułowany na pierwszy namacalny krok bramki (np. "otwórz `*.plan.md` i zatwierdź/odrzuć zakres przed startem kodu").

To odróżnia szkielet strony PM od pozostałych pięciu (które mają naturalny 1-command Quick Start) — do rozstrzygnięcia w Planie, czy Krok 1 (Quick Start) dla PM dostaje wariant tekstowy zamiast bloku kodu z komendą.
