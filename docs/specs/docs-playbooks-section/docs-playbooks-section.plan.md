## Wildly Important Goal

**Goal**: Ship a "Team Guides" docs section (landing + 6 role pages) where every referenced command/skill is verified to exist in this repo, each page follows an identical 6-part how-to skeleton, and the section is reachable from the sidebar at the agreed position.

**Success Measure**: `cd website && npm run build` succeeds with zero broken links/Mermaid errors, "Team Guides" renders in the sidebar between "Workflow" and "Agents", and every `/eversis-*` command or skill id named across the 7 new pages appears in Research §2.3's verified inventory (no fabricated names).

**Do NOT touch / do NOT add**:
- Any existing file under `website/docs/**` outside the new `team-guides/` folder.
- `website/sidebars.ts` (autogenerated tree already covers new folders) or `website/docusaurus.config.ts` (Mermaid already configured).
- `position` values on any existing `_category_.json` (Getting Started=2, Workflow=3, Agents=4, Prompts=5, Skills=6, Integrations=7) — use a fractional `3.5` instead of renumbering.
- `.ai/rules/`, `.ai/skills/`, `.ai/prompts/` source content — pages reference it, never edit it.
- New npm dependencies — Mermaid support already present via `@docusaurus/theme-mermaid`.
- Creating an actual Project Manager agent/prompt/skill — that gap is documented, not filled, in this task (see Research §3; tracked as a follow-up in Improvements).

## Proposed Solution

Add `website/docs/team-guides/` with 8 files: `_category_.json` (label "Team Guides", `position: 3.5`, `collapsible: true`), `index.md` (landing), and one page per role. Every role page follows the identical skeleton fixed by the approved research (English, matching the site's existing language):

1. Hero / TL;DR (one sentence + one anchor link to Quick Start)
2. Quick Start — your first 5 minutes (one ready-to-run command, or for Project Manager a first concrete gate-review step instead of a command — Research §3/§4 Q4)
3. Daily scenarios table (`| Situation | What you do | Agent/Skill/Prompt | What you get |`, ≥4 rows, each tagged `[Greenfield]` or `[Maintenance]`, ≥1 of each)
4. How you connect to other roles — Mermaid `flowchart LR` with ≥2 neighboring roles + a `| Your output | Goes to role | As artifact |` table
5. Command cheat sheet — short bulleted reference block, visually set apart (blockquote or admonition), only commands/skills verified in Research §2.3
6. Next steps — max 3 links (lifecycle doc, most-adjacent role's playbook, an advanced section if one exists)

A static Markdown link list ("Other guides: …") repeated at the top of each page serves as the role picker (Q1, resolved) — no new React component. The landing page (`index.md`) is one intro paragraph + a Markdown table of the 6 roles with a one-sentence benefit and a link (Q2, resolved) — no duplication of page content.

## Technical Context

Project conventions discovered during planning. Downstream execution (this same session) reads this instead of re-discovering context.

### Project Instructions

- `CLAUDE.md` (root) → orchestration rules: repository documentation tasks route to **Repo Docs Writer** via [`eversis-repo-docs-writer.md`](../../../.ai/prompts/public/eversis-repo-docs-writer.md), guided by skill `eversis-writing-repo-documentation` — load that skill before authoring page content.
- Hard limits (`.ai/rules/orchestration/agent-core.md`): no edits outside task scope without approval, no new package-manager dependencies, no silent removal/shortening of documentation comments.
- Task's own hard requirement (carried from the original instruction, still binding): zero fabricated commands/agents/skills — every reference must be checked against Research §2.2/§2.3.

### Architecture & Patterns

- Docusaurus 3, classic preset, single autogenerated sidebar tree (`dirName: '.'`).
- Top-level section = folder under `website/docs/` + `_category_.json` with `label`/`position`/`collapsible` — no other registration step.
- Existing docs favor tables and short admonitions (`:::tip`, `:::info`, `:::warning`) over long prose (seen throughout `intro.md`, `workflow/overview.md`).

### Tech Stack

- Docusaurus `^3.x`, `@docusaurus/theme-mermaid@3.10.2` (already a dependency — do not add).
- Build: `npm` in `website/` (`package.json` scripts).

### Code Style & Standards

- English content (site-wide convention — all existing `docs/` pages are English; task instructions were Polish but target content language follows the site, per "keep tone consistent with existing content").
- Gloss jargon on first use per page (e.g. "SSOT (Single Source of Truth)", "MCP (Model Context Protocol)") — mirrors the task's own explicit requirement and existing site practice (e.g. `intro.md` glosses acronyms on first use).
- Bold key terms, prefer tables/lists over paragraphs, matching neighboring `workflow/*.md` pages.
- Every command/skill name mentioned must match an id from Research §2.2 verbatim (`eversis-<kebab-name>`), no invented shorthand.

### Testing Patterns

- No test framework for docs content. Verification command: `cd website && npm run build` (fails on broken links per Docusaurus default `onBrokenLinks: "throw"`, and on Mermaid syntax errors).
- Run the build after Phase 1 (scaffold) and again after Phase 2 (full content) — cheap, catches broken links/Mermaid errors early rather than only at the end.

### Additional Context

- Word budget: **≤600 words** of body content per role page, excluding tables and code/command blocks — a ceiling, not a floor, per the task's own instruction ("maximum 500-600 words... if you exceed, cut") and its stated priority of UX/readability over completeness. Cut content rather than add a 7th section if over budget; being under 500 is not itself a defect.
- Scenario table columns are fixed verbatim: `| Situation | What you do | Agent/Skill/Prompt | What you get |` (English equivalent of the task's Polish column spec, translated for site-language consistency) — at least 4 rows per page, at least one `[Greenfield]` and one `[Maintenance]` tag.
