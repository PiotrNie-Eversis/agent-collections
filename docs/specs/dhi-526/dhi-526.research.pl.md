**User story:** Jako backend developer używający Claude Code CLI chcę `CLAUDE.md` wygenerowany z core, żeby sesje CLI trzymały te same standardy architektury i jakości co użytkownicy Cursor.

## Wpływ biznesowy

Domknięcie **drugiego kanału MVP** (Cursor + Claude): bez adaptera Claude Code pilota EOG (backend na Claude) i wizarda instalacji (5.6) nie da się uczciwie oznaczyć Claude jako `shipped`. Wspólny SSOT `.ai/` + dwa generatory (Cursor już istnieje) to warunek „jedna treść reguł → wiele narzędzi”.

## Kryteria akceptacji (z Jira)

1. GIVEN core rules i domeny backend-relevant WHEN Claude adapter działa THEN powstaje `CLAUDE.md` z **directory scope**, instrukcjami CLI-oriented oraz guidance warstwy systemowej
2. GIVEN wygenerowany `CLAUDE.md` WHEN start zadania backend w Claude Code THEN agent dostaje wystarczający kontekst **bez** ładowania plików Cursor-specific
3. GIVEN layout monorepo WHEN scoped THEN ścieżki backend są włączone, a niepowiązane frontend / tool config wyłączone wg reguł izolacji (**Work Stream 3**)
4. Dziedziczone AC SDD (folder spec, research → plan → implement → review → Fine)

| Fakt | Implikacja dla DHI-526 |

| Project instructions: `./CLAUDE.md` **lub** `./.claude/CLAUDE.md` | Spec 523 wybiera root `CLAUDE.md` — zgodne z oficjalnym wariantem |
| Zalecenie: **&lt; ~200 linii** na plik `CLAUDE.md` | Suma ciał zmapowanych reguł Cursor (~300+ linii samych bodies) **przekracza** rekomendację przy pełnym inline → Gap Q2 (inline vs `@import` vs `.claude/rules/`) |

## Gap Analysis

### Pytanie 1
#### Jaki **kształt wyjścia** ma mieć MVP względem oficjalnego Claude Code (przy zachowaniu ducha DHI-523 Q4 = jeden `CLAUDE.md`)?
**Opcje:**  
**A)** Strict 523: **tylko** root `CLAUDE.md` z H2 per rule (bez `.claude/rules/`) — scope opisany instrukcyjnie w pliku  
**B)** Hybrid: root `CLAUDE.md` (orchestration + how-to) + wygenerowane `.claude/rules/*.md` z `paths:` dla domen (lepsze AC #1/#3, wymaga **dopisku** do mapping spec)  
**C)** Tylko `.claude/CLAUDE.md` + `.claude/rules/` (bez root `CLAUDE.md`) — odbiega od §5 mapping  

**Rekomendacja research:** **A** dla zgodności ze spekiem 523 w pierwszej fali; **B** jeśli AC „directory scope” ma być natywnie egzekwowane już w 526 (wtedy mały DELTA do `adapter-mapping.md`).

### Pytanie 2
#### Jak wstawiać **treść** reguł do `CLAUDE.md` (limit ~200 linii w docs Anthropic)?
**Opcje:**  
**A)** Pełny inline body każdej zmapowanej reguły (jak szkic §5.2) — proste, ale plik >> 200 linii (~300+ samych bodies z mapy Cursor)  
**B)** Inline tylko orchestration always-on + krótkie streszczenia / pointery `@.ai/rules/...` dla reszty (import ładuje przy starcie — nadal koszt kontekstu)  
**C)** Kondensacja / skróty generowane (ryzyko drift vs SSOT)  

**Rekomendacja research:** **A** jeśli priorytetem jest wierność SSOT i prostota generatora (świadomy trade-off tokenów); **B** jeśli priorytetem jest adherence / rozmiar kontekstu. Unikać **C** bez osobnej story jakości.

### Pytanie 3
#### Nazwa katalogu adaptera i współdzielenie mapy z Cursor?
**Opcje:**  
**A)** `adapters/claude/` + **osobny** `rule-map.yaml` (te same `id`/`source`, bez pól Cursor)  
**B)** `adapters/claude-code/` + osobna mapa (nazwa zgodna z brandingiem narzędzia)  
**C)** Jedna wspólna mapa `adapters/shared/rule-map.yaml` + generatory czytają subset pól  

**Rekomendacja research:** **A** — spójne z diagramem w `adapter-mapping.md` (`adapters/claude/`); wspólna mapa (C) można odłożyć do DHI-527.

### Pytanie 4
#### Które reguły wchodzą do MVP względem AC „backend-relevant domains”?
**Opcje:**  
**A)** Ten sam zestaw co Cursor `rule-map.yaml` (7 id) — spójność cross-tool; frontend accessibility też w pliku (scope „backend” tylko w narracji user story)  
**B)** Podzbiór: orchestration + backend + architecture (+ shared-types) — bez frontend accessibility  
**C)** Profilowalny generator (`--profile backend|full`) — większy zakres story  

**Rekomendacja research:** **A** dla MVP framework repo (parity z Cursor); **B** jeśli trzymamy się literalnie user story „backend developer”. Profil **C** → raczej DHI-527 / installer.

### Pytanie 5
#### Jak traktować AC #3 (monorepo isolation / WS3) w tej story?
**Opcje:**  
**A)** **DEFER** pełną izolację do DHI-528–530; w 526 tylko: brak Cursor paths w emit + sekcja instrukcyjna „prefer backend trees / nie ładuj `.cursor`” + checklist w planie  
**B)** Minimalny emit wspierający scope już teraz (np. `.claude/rules` + `paths` **lub** przykładowy `claudeMdExcludes` w docs — bez pełnego ignore sync)  
**C)** Pełne `.claudeignore` + ustawienia monorepo w zakresie 526 (wciąga WS3)  

**Rekomendacja research:** **A** (granica sibling stories już w mapping §8); **B** tylko jeśli Q1=B.

### Pytanie 6
#### Czy wygenerowany `CLAUDE.md` commitować w **tym** repo frameworka?
**Opcje:**  
**A)** Tak — commit `CLAUDE.md` + generator; re-run w CI/docs jak Cursor `.mdc`  
**B)** Generator w repo; `CLAUDE.md` generowany przy install / lokalnie (niekoniecznie committed w framework)  
**C)** Tylko generator + fixture w `adapters/claude/fixtures/` do testów; root `CLAUDE.md` opcjonalny  

**Rekomendacja research:** **A** — analogicznie do wygenerowanych `.cursor/rules/*.mdc` w tym repo po DHI-524; ułatwia dogfooding Claude na frameworku.
