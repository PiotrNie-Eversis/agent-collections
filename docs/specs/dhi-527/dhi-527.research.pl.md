**User story:** Jako maintainer frameworka chcę jedną komendę regenerującą wszystkie adaptery z core, żeby aktualizacje reguł pozostały zsynchronizowane między narzędziami (Cursor, Claude, …).

## Wpływ biznesowy

Domknięcie **Work Stream 2 tooling**: bez wspólnego sync maintainer musi ręcznie odpalać `node adapters/cursor/generate.mjs` i `node adapters/claude/generate.mjs` (i pamiętać o checkach). To jest warunek utrzymania inwariantu „jedna zmiana w `.ai/` → spójne wyjścia tooli” oraz wejście pod **installer / upgrade** (Story 5.2 zależna od 2.5). AC „project-owned preserved” chroni kontrakt upgrade z root `README.md` (nie nadpisywać stacku / context / secrets).

## Kryteria akceptacji (z Jira)

1. GIVEN zaktualizowane core rules WHEN uruchomiona komenda sync THEN wyjścia **Cursor** i **Claude** regenerują się **deterministycznie**
2. GIVEN projekt konsumencki WHEN sync działa THEN zmieniają się **tylko** wygenerowane wyjścia adapterów; **project-owned** configuration pozostaje nietknięta
3. GIVEN CI lub walidacja lokalna WHEN sync kończy się THEN krok **diff / validation** potwierdza brak driftu między core a adapterami
4. Dziedziczone AC SDD (folder spec, research → plan → implement → review → Fine)

## Gap Analysis

### Pytanie 1
#### Gdzie ma żyć **entrypoint** sync CLI w tym repo?
**Opcje:**  
**A)** `adapters/sync.mjs` (lub `adapters/generate-all.mjs`) — obok generatorów; wywołanie `node adapters/sync.mjs`  
**B)** `scripts/sync-adapters.mjs` — legacy-style jak cursor-collections `scripts/` (+ opcjonalnie później `package.json`)  
**C)** Minimalny `package.json` z `"scripts": { "sync:adapters": "node …" }` **oraz** plik z A lub B  

**Rekomendacja research:** **A** (spójne z `adapters/*/generate.mjs`, zero npm obowiązkowego); **C** jako dodatek jeśli chcesz `npm run …` bez wymuszania instalacji deps (pusty / scripts-only package).

### Pytanie 2
#### Które adaptery wchodzą w **MVP sync** względem AC („Cursor and Claude”)?
**Opcje:**  
**A)** **Tylko** Cursor + Claude (literalne AC) — OpenCode poza komendą (docs: „placeholder nie wymaga regeneracji treści”)  
**B)** Cursor + Claude + **no-op / validate** OpenCode (np. sprawdź istnienie `opencode.jsonc` + status block; bez przepisywania bez potrzeby)  
**C)** Cursor + Claude + „regeneruj” OpenCode z szablonu adaptera (ryzyko nadpisania lokalnych tweaków placeholdera)  

**Rekomendacja research:** **A** (zgodność z AC); **B** tylko jeśli chcesz jedną komendę „wszystkie maturity shipped|placeholder health”.

### Pytanie 3
#### Jak zrealizować AC #3 (**diff / validation**, brak drift)?
**Opcje:**  
**A)** Flaga `--check`: generacja do katalogu tymczasowego → porównanie bajt-po-bajcie / znormalizowane LF z plikami docelowymi; exit ≠ 0 przy różnicy  
**B)** Sync zawsze pisze; osobny skrypt `check-adapters-drift.mjs` używany w CI  
**C)** Tylko dokumentacja „uruchom sync i `git diff --exit-code` na allowlist ścieżek” — bez dedykowanego trybu  

**Rekomendacja research:** **A** (jedna komenda spełnia AC lokalnie i w CI: `node adapters/sync.mjs --check`).

### Pytanie 4
#### Czy sync w MVP celuje w **framework repo** tylko, czy także ścieżkę **consumer** (`--out` / target)?
**Opcje:**  
**A)** Framework-first: domyślnie root tego repo; `--out` jak w generatorach (wystarczy dogfood + submodule layout)  
**B)** Pełny consumer mode (discovery target, merge MCP, recorded agents) — wciąga 5.x  
**C)** Framework + jawny `--out` **oraz** krótki docs „consumer: wskaż checkout framework / out” bez installera  

**Rekomendacja research:** **A** lub **C**; unikać **B** (installer).

### Pytanie 5
#### Czy DHI-527 łączy mapy reguł w **shared** `rule-map`?
**Opcje:**  
**A)** **Nie** — orkiestracja tylko; mapy Cursor/Claude zostają osobne (parity id/source już jest)  
**B)** Wspólny plik `adapters/shared/rule-map.yaml` + generatory czytają subset (większy refaktor 524/526)  
**C)** Tylko dokumentacja / test, że id/source sets są równe (assert w sync `--check`) bez merge plików  

**Rekomendacja research:** **A** dla zakresu story; **C** jako lekki bonus w `--check` (wykryj rozjazd map).

### Pytanie 6
#### Jak głęboko iść z **CI** w tej story?
**Opcje:**  
**A)** Tylko lokalny `--check` + docs „dodaj do CI”; bez nowego workflow w repo (jeśli CI jeszcze nie istnieje)  
**B)** Dodać / podpiąć job CI uruchamiający `sync --check`  
**C)** Pre-commit hook  

**Rekomendacja research:** **A** (repo nie ma dziś `package.json`/CI adapters); **B** jeśli maintainer chce hardening w tym samym PR.
