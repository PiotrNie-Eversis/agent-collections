**User story:** As an AI agent in any tool, I want a standard `AGENTS.md` format so that I can locate project areas, roles, and framework entry points consistently.

## Business Impact

Closes **Work Stream 4.1** — agnostic orientation layer required by [`docs/architecture/isolation-strategy.md`](../../architecture/isolation-strategy.md): a small, dense monorepo + role map instead of dumping the whole tree into session context. Without the template:

- consumers keep a Cursor-only stub,
- Claude / OpenCode lack a shared entry (OpenCode already points at future `AGENTS.md` in the mapping spec),
- install wizard (5.x) has nothing to seed with placeholders,
- Story **4.2** (DHI-532) has no structure to fill as this repo’s reference.

## Gap Analysis

### Question 1
#### Where does the **committed** AGENTS template deliverable live, and how do project deliverable folders relate?

**Options (original):**  
**A)** `templates/AGENTS.template.md` only  
**B)** `docs/architecture/agents-md-standard.md` only  
**C)** Both architecture standard + copyable `templates/`  
**D)** Only replace root `AGENTS.md`

**Decision (2026-08-06):** **C**, with layout policy:

1. **Committed AGENTS story deliverables:** `docs/architecture/agents-md-standard.md` + `templates/AGENTS.template.md` (+ README / `.ai/README.md` pointers). Not under `docs/specs/dhi-*`.
2. **Project agent deliverables** (any repo using the framework): **`docs/context/`**, **`docs/plans/`**, **`docs/specs/`** — same triad as cursor-collections. The AGENTS standard/template **must document** this triad.
3. **`docs/specs/dhi-*/` (and similar framework-local story folders)** stay **gitignored** — local-only work on the framework itself, not published product content.

### Question 2
#### Boundary **DHI-531 vs DHI-532** for root `AGENTS.md`?

**Decision:** **B** — DHI-531 restructures root `AGENTS.md` to the template section shape with placeholders / short framework pointers (no full reference fill). DHI-532 fills the complete reference (areas, maintainer roles, install entry points).

### Question 3
#### What goes in the **role matrix**?

**Decision:** **A** — framework **agent roles** only (full orchestration set, one line each: purpose + entry id). Human team hints live in **Monorepo / Areas** (or Project specifics), not a second heavy matrix.

### Question 4
#### How deep is AC #3 (install/bootstrap) in **this** story?

**Decision:** **A** — install **contract** only (template source path, placeholder semantics, create-if-absent, never overwrite existing). CLI wiring deferred to install stories (5.2 / 5.6). Do not update legacy cursor-collections stub in this story.

### Question 5
#### Cursor UX (`@` / `.cursor/`) in the template?

**Decision:** **A** — main body has **zero** `@` / `.cursor/` as primary instructions; optional appendix **“Channel notes (Cursor)”**.

**Clarification (maintainer ask):** Does Q5=A still allow using **`/eversis-implement`** and **`@eversis-implement`** together in Cursor like cursor-collections?

**Answer: Yes.** Q5=A only governs what `AGENTS.md` *documents* in its agnostic body. It does **not** remove Cursor channel packaging:

| Mechanism | What it is | Still works on Cursor? |
|-----------|------------|-------------------------|
| `/eversis-implement` | Cursor **command** (`.cursor/commands/…` when the Cursor adapter ships/scaffolds commands) | Yes — adapter/channel concern |
| `@eversis-implement` | Cursor **prompt attach** by file stem under prompts | Yes — adapter/channel concern |
| Prompt id `eversis-implement` | Tool-neutral name in AGENTS body / Claude / OpenCode | Yes — canonical reference |

The optional Cursor appendix **should** state that on the Cursor channel both `/eversis-implement` and `@eversis-implement` remain valid ways to start Implement (parity with cursor-collections). Claude/OpenCode ignore that appendix.

### Question 6
#### Language of committed template / framework content?

**Decision:** **A** — **English only** for the **entire** framework (templates, architecture, rules, skills, prompts, README, AGENTS, docs site content). Polish is **not acceptable** for framework product content. Local SDD artifacts for this epic are also English going forward (`*.research.md` / `*.plan.md`, not `*.pl.md`).
