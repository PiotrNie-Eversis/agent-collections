**User story:** Jako właściciel projektu konsumenckiego chcę mieć udokumentowany sposób upgrade z centralnego frameworka `agent-collections`, żeby ulepszenia propagowały się bez pełnej reinstalacji od zera.

## Wpływ biznesowy

Zamyka lukę WNF-02 („upgrade bez wycierania plików projektowych”) na poziomie **kontraktu** — zanim DHI-537 dostarczy przetestowaną ścieżkę konsumencką z instalera. Umożliwia spójne tagowanie release’ów, changelog breaking changes oraz bezpieczne pinowanie przez submodule / tag / przyszły `--version`.

## Kryteria akceptacji (z Jira)

1. Projekt na wersji N → po publikacji N+1 istnieje **udokumentowana** ścieżka upgrade (sync, bump submodule **lub** CLI upgrade)
2. Kontrakt upgrade **nigdy nie nadpisuje** plików project-owned (np. project stack, lokalny context) bez **explicit opt-in**
3. Breaking change w release → **odnotowany w changelog frameworka** z krokami migracji
4. Dziedziczone AC SDD (folder spec, research → plan → implement → review → Fine)
