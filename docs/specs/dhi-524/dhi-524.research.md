**User story:** As a frontend developer using Cursor, I want `.cursor/rules/*.mdc` files generated from the core so that I get the same standards as today without maintaining duplicate rule files.

## Business Impact

First **shipped** Work Stream 2 generator: closes “core SSOT → Cursor native”. Unblocks self-contained bootstrap (DHI-533), sync tooling (DHI-527), glob isolation (DHI-528–530), installer/wizard (5.x), and EOG pilot (Cursor frontend). Without it, the repo stays dependent on symlinks to `cursor-collections`.

## Acceptance Criteria (from Jira)

1. **Generation:** GIVEN core rules with domain scope WHEN the Cursor adapter runs THEN `.cursor/rules/*.mdc` files are generated with appropriate `globs` / `description` / `alwaysApply` front matter
2. **Behaviour parity:** GIVEN generated rules WHEN loaded in Cursor THEN orchestration, code quality, and **project-stack customization** behave equivalently to the legacy framework for a reference project
3. **Re-run:** GIVEN a core rule update WHEN the adapter re-runs THEN Cursor rules update without manual editing of generated files
4. Inherited SDD AC (spec folder, research → plan → implement → review → Fine)

## Gap Analysis

### Question 1
#### Generator **runtime / language** for this story?
**Options:**  
**A)** Node.js (e.g. `adapters/cursor/generate.mjs`) + minimal run path  
**B)** Pure bash  
**C)** Python  
**D)** `rule-map.yaml` + sample `.mdc` only in 524; full generator in **DHI-527**  

**Explanation:** AC #3 needs a real re-run generator — D fails that intent. Bash gets fragile with YAML/escaping; Python works but Node fits Cursor/Agent Collections tooling better.  

**Recommendation:** **A**. Avoid **D**.

**Answer (approved 2026-08-05):** **A**

### Question 2
#### Initial **rule-map** entry scope?
**Options:**  
**A)** Legacy-equivalent framework five only (agent-core, testing-and-terminal, accessibility, engineering-manager, code-reviewer)  
**B)** All 11 `.ai/rules/**/*.md` content files  
**C)** Legacy five **plus** new orchestration (`fine-handoff`, `spec-driven-development`); domain seeds later  

**Explanation:** A matches today’s Cursor surface (minus BA) but misses SDD/Fine. B forces packaging guesses for thin seeds. C closes orchestration Delivery Standard without unsafe seed globs.  

**Recommendation:** **C**.

**Answer (approved 2026-08-05):** **C**

### Question 3
#### **BA Docs** planner/writer (legacy `.mdc`, no core rules — deferred DHI-519)?
**Options:**  
**A)** Out of DHI-524 — do not generate; drop BA symlinks when switching to generated rules  
**B)** Temporarily keep BA symlinks to `cursor-collections` only  
**C)** Add thin BA core rules in this story and map them  

**Explanation:** C reopens deferred content extraction. A is clean but removes BA attach UX. B is hybrid ugly but zero BA regression.  

**Recommendation:** **B** (document as temporary). **A** OK if BA attach loss is accepted until a follow-up story.

**Answer (approved 2026-08-05):** **B**

### Question 4
#### **`eversis-project-stack.mdc`** (AC #2 mentions project-stack parity)?
**Options:**  
**A)** Never generate/overwrite — keep local file; AC #2 = local stack still works beside generated rules  
**B)** Emit template outside `.cursor/rules/` only  
**C)** Generate into `.cursor/rules/` only with opt-in flag  

**Explanation:** DHI-521 / README: consumer-owned. AC #2 means parity of *customization still working*, not generating stack from core. C risks wipe. B is installer nicety, not blocking.  

**Recommendation:** **A**.

**Answer (approved 2026-08-05):** **A**
