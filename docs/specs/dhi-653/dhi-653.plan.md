## Wildly Important Goal

**Goal**: The header navbar presents the same 4 intent-based clusters as the sidebar, so the two persistent navigation surfaces on every page agree with each other instead of showing two different taxonomies.

**Success Measure**: The navbar's cluster-matching items are reduced from 8 fragmented entries to 4 (Get started, The Main Flow, Reference, Advanced / CTO), each a direct link to that cluster's landing page, and `cd website && npm run build` succeeds with zero broken links.

**Do NOT touch**: Any file other than `website/docusaurus.config.ts`; the `Docs` sidebar-toggle item, `Changelog`, and GitLab items (explicitly out of scope per the ticket AC); the cluster landing pages themselves (read-only reference, not modified); no dropdown menus are created (research Question 2, superseded by stakeholder decision — plain links only).

## Proposed Solution

Replace the 6 navbar items that fragment the 3 already-merged clusters (`Framework`, `Isolation`, `Workflow`, the `Components` dropdown, `Use Cases`, `For CTOs`) with exactly 3 new plain-link items — one per cluster, each linking directly to that cluster's `index.md` landing page, following the same pattern the existing `Get started` item already uses (a direct link to its cluster's landing/first page, no dropdown):

```text
Before (8 cluster-related items):
Get started | Framework | Isolation | Workflow | Components ▾ | Use Cases | For CTOs

After (4 cluster-matching items):
Get started | The Main Flow | Reference | Advanced / CTO
```

`Docs`, `Changelog`, and the GitLab link are untouched — they aren't docs-IA content, they're utility links (per research and the ticket AC).

## Technical Context

### Project Instructions

- Routing: `website/docusaurus.config.ts` is site configuration, not `.md` content — but it's still within `website/` docs-site scope per the Repo Docs Writer's `README, CHANGELOG, docs/, website/docs` remit interpreted broadly for this framework (the same file was already hand-edited during DHI-641/DHI-642 for the equivalent href-only fix, by the same routing). No Software Engineer delegation needed — this is a config object literal edit, not application logic.

### Architecture & Patterns

- Docusaurus navbar items: `{ to: string, label: string, position: "left" | "right", className?: string }` for plain links (see existing `Get started`, `Changelog`, `For CTOs` items) vs. `{ type: "dropdown", label, position, items: [...] }` for menus (see existing `Components` item, being removed). This plan only uses the plain-link shape.

### Tech Stack

- TypeScript config object (`docusaurus.config.ts`), no new dependencies.

### Code Style & Standards

- Match existing navbar item formatting exactly (4-space indent inside the array, `to`/`label`/`position` key order, trailing comma) — see the `Get started` item as the template.

### Testing Patterns

- `cd website && npm run build` — `onBrokenLinks: "throw"` validates the new `to` targets (`/docs/main-flow`, `/docs/reference`, `/docs/advanced`) resolve to real pages. This is the only verification surface for this task (no unit test applies to a config literal).

### Database Patterns

Not applicable.

### Additional Context

- The 3 new `to` targets (`/docs/main-flow`, `/docs/reference`, `/docs/advanced`) are the landing `index.md` pages created during DHI-641 Phase 2 — none of them carry a custom `slug:` frontmatter override, so their route is exactly their file path (confirmed pattern from DHI-641's own research: only `domain-context.md`, `isolation.md`, and `framework-reference.md` have custom slugs; these 3 index pages do not).
