**User story:** Jako developer chcę mieć `.cursorignore`, `.claudeignore` i `.opencodeignore` dostarczone przez framework, żeby reguły wykluczeń były spójne między narzędziami.

## Wpływ biznesowy

Materializuje oś **cross-tool packaging** z Work Stream 3: bez triady ignore narzędzia indeksują nawzajem swoje powierzchnie opakowania (`.cursor/**`, `CLAUDE.md`, `opencode.jsonc`), co psuje izolację kontekstu w monorepo i blokuje wiarygodny pilot WNF-03 (DHI-542). Story 3.2 odblokowuje instalera (Story 5.2 wymaga ignore w bundlu) oraz domyka kontrakt §8.1 strategii izolacji.

## Kryteria akceptacji (z Jira)

1. Po instalacji frameworka obecne są **wszystkie trzy** pliki ignore ze **zsynchronizowanymi** wzorcami wykluczeń
2. Gdy Claude Code indeksuje repo — ścieżki Cursor-specific (np. `.cursor/rules` / stuby) są **wykluczone** z kontekstu Claude
3. Gdy Cursor indeksuje — ścieżki Claude-specific (np. `CLAUDE.md` / config Claude) są **wykluczone** z kontekstu Cursor
4. Dziedziczone AC SDD (folder spec, research → plan → implement → review → Fine)

## Gap Analysis

### Pytanie 1
#### Gdzie ma żyć **committed** deliverable triady w tej story (installer jeszcze nie istnieje)?
**Opcje:**  
**A)** Tylko **root** repo `agent-collections` (`.cursorignore` + nowe `.claudeignore` + `.opencodeignore`) — doggie-food frameworka; installer (5.2) skopiuje / zmerguje później  
**B)** Tylko **szablony** (np. `templates/ignore/` lub pod `adapters/`) — root frameworka zostaje minimalny  
**C)** **Dual:** root triad (framework) **oraz** skopiowalne szablony dla konsumenta  

**Odpowiedź (zatwierdzona 2026-08-06):** **A** — tylko root repo `agent-collections`.

### Pytanie 2
#### Jak utrzymać **synchronizację** trzech plików (AC #1 „synchronized exclusion patterns”)?
**Opcje:**  
**A)** Trzy ręczne pliki + checklista w docs / CI smoke (np. skrypt sprawdzający obecność klas)  
**B)** Jeden SSOT (YAML/JSON klas) + generator emitujący trzy pliki (nowy mały skrypt; poza `adapters/sync.mjs` lub opcjonalnie podpięty)  
**C)** Wspólny fragment tekstowy + cienkie wrappery per tool  

**Odpowiedź (zatwierdzona 2026-08-06):** **A** — trzy ręczne pliki + checklista klas w docs (bez generatora).

### Pytanie 3
#### Czy triad w **repo frameworka** ma zawierać wzorce **heavy-infra** (§6) i abstrakcyjne `apps/**`, skoro `agent-collections` nie jest monorepo aplikacyjnym?
**Opcje:**  
**A)** Tak — pełny zestaw konsumencki także w root (nawet jeśli część wzorców jest no-op lokalnie)  
**B)** Nie w root — root = cross-tool packaging + secrets/build; heavy-infra / area excludes tylko w szablonach konsumenckich (lub DHI-530)  
**C)** Root = packaging + secrets/build + **komentowany** blok heavy-infra do odkomentowania u konsumenta  

**Odpowiedź (zatwierdzona 2026-08-06):** **B** — root = cross-tool packaging + secrets/build; bez heavy-infra / `apps/**`.

### Pytanie 4
#### Czy `adapters/sync.mjs` / generate ma **emitować** lub weryfikować ignore w tej story?
**Opcje:**  
**A)** Nie — ignore pozostaje plikami static / osobnym skryptem; sync MVP bez zmian (zgodnie z obecnym README)  
**B)** Tak — dodać krok generate/check ignore do sync  
**C)** Tylko `--check` obecności triady / klas; bez generowania treści  

**Odpowiedź (zatwierdzona 2026-08-06):** **A** — sync bez zmian; ignore = pliki static.

### Pytanie 5
#### Polityka względem **istniejącego** consumer `.cursorignore` przy przyszłej instalacji (kontrakt pod 5.2 — ustalić teraz, żeby triad była kompatybilna)?
**Opcje:**  
**A)** Framework dostarcza **fragmenty / szablony**; installer **merguje** braki, nigdy nie wyciera lokalnych wpisów bez opt-in  
**B)** Installer nadpisuje pliki ignore frameworkowe w całości (breaking względem DHI-521 — niezalecane)  
**C)** Installer zapisuje tylko brakujące pliki (`.claudeignore` / `.opencodeignore`); istniejące `.cursorignore` zostawia nietknięte + dokumentuje ręczne dopisanie klas  

**Odpowiedź (zatwierdzona 2026-08-06):** **A** — kontrakt docelowy: merge braków / opt-in (implementacja merge = 5.2; w 529 kształt sekcji pod łatwy merge).
