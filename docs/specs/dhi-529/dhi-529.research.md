**User story:** As a developer, I want `.cursorignore`, `.claudeignore`, and `.opencodeignore` provided by the framework so that exclusion rules stay consistent across tools.

## Business Impact

Materializes the **cross-tool packaging** axis of Work Stream 3. Without the ignore triad, tools index each other’s packaging (`.cursor/**`, `CLAUDE.md`, `opencode.jsonc`), breaking collision-free context and blocking credible WNF-03 pilot work (DHI-542). Story 3.2 also unblocks the installer bundle (Story 5.2) and closes isolation-strategy §8.1.

## Acceptance Criteria (from Jira)

1. After framework installation, **all three** ignore files are present with **synchronized** exclusion patterns
2. When Claude Code indexes the repo — Cursor-specific paths (e.g. `.cursor/rules` stubs) are **excluded** from Claude’s context
3. When Cursor indexes — Claude-specific paths (e.g. `CLAUDE.md` / Claude config) are **excluded** from Cursor’s context
4. Inherited SDD ACs (spec folder, research → plan → implement → review → Fine)

## Gap Analysis

### Question 1
#### Where should the **committed** triad live in this story (installer not yet built)?
**Options:**  
**A)** Framework **repo root** only (extend `.cursorignore` + add the other two)  
**B)** **Templates only** (e.g. `templates/ignore/`)  
**C)** **Dual:** root triad **and** copyable consumer templates  

**Answer (approved 2026-08-06):** **A** — framework repo root only.

### Question 2
#### How to keep the three files **synchronized** (AC #1)?
**Options:**  
**A)** Three hand-maintained files + docs/CI checklist of required classes  
**B)** One SSOT (YAML/JSON) + small generator emitting three files  
**C)** Shared text fragment + thin per-tool wrappers  

**Answer (approved 2026-08-06):** **A** — three hand-maintained files + docs checklist of classes (no generator).

### Question 3
#### Should the **framework-repo** triad include **heavy-infra** (§6) / abstract `apps/**` patterns even though this repo is not an app monorepo?
**Options:**  
**A)** Yes — full consumer-oriented set in root  
**B)** No in root — root = cross-tool packaging + secrets/build; heavy/area patterns in consumer templates or DHI-530  
**C)** Root = packaging + secrets/build + **commented** heavy-infra block  

**Answer (approved 2026-08-06):** **B** — root = packaging + secrets/build only; no heavy-infra / `apps/**`.

### Question 4
#### Should `adapters/sync.mjs` emit or verify ignore files in this story?
**Options:**  
**A)** No — static files / separate script; sync MVP unchanged  
**B)** Yes — add generate/check to sync  
**C)** `--check` presence/classes only; no content generation  

**Answer (approved 2026-08-06):** **A** — sync unchanged; ignore files remain static.

### Question 5
#### Future installer policy for an **existing** consumer `.cursorignore` (set now for 5.2 compatibility)?
**Options:**  
**A)** Framework ships fragments/templates; installer **merges** missing entries; never wipe without opt-in  
**B)** Installer overwrites ignore files wholesale (conflicts with DHI-521 — not recommended)  
**C)** Installer only creates missing files (`.claudeignore` / `.opencodeignore`); leaves existing `.cursorignore` alone + documents manual class adds  

**Answer (approved 2026-08-06):** **A** — target contract: merge missing / opt-in (merge implementation = 5.2; this story shapes sections for easy merge).
