## Business Impact

`eversis-ba-docs-planner` and `eversis-ba-docs-writer` depend on `inspect_document` before a verified plan or the first edit. When the call returns `Not a file`, the planner correctly falls back to `plan_status: UNVERIFIED`, and the writer is required to inspect before editing, so the same error blocks the write. The ticket records a live block on DHI-661 (SVR update) in the `eog` consumer repo.

Repro from the ticket (consumer repo `eog`):

1. Host file `~/Downloads/DAWIS_EOE_Software_Validation_Report_SVR_v1.0.docx` exists (`file` reports Microsoft Word 2007+, 206483 bytes).

### Codebase

This repository is the Agent Collections framework. The MCP server is `mcp/eversis-collections-mcp` (TypeScript, stdio). It is packaged as a container via `mcp/eversis-collections-mcp/Dockerfile` and `docker-compose.yml`.

Two bind mounts already exist (`docker-compose.yml`):

| Mount | Container path | What it is |
|---|---|---|
| `.` (compose-file directory) | `/repo` | Framework checkout. `AGENT_COLLECTIONS_HOME=/repo`. |
| `${CONSUMER_PROJECT_ROOT:-${PWD}}` | `/workspace` | Consumer project. Inside the container `CONSUMER_PROJECT_ROOT=/workspace`. |

The image `WORKDIR` is `/app` (`Dockerfile`, runtime stage). `/app` holds `dist/` and `node_modules`. It is not a volume. Nothing from the host project is copied there at runtime.

Domain-context tools do not use `process.cwd()`. `resolveWorkspaceRootFrom` in `mcp/eversis-collections-mcp/src/context.ts` returns `CONSUMER_PROJECT_ROOT` when that directory contains `.agent-collections/install-selection.json`, otherwise `/workspace` when that mount has the same file, otherwise `cwd`.

Docx tools do not use that helper. They call `path.resolve`, which is relative to `process.cwd()` (`/app` in the container):

- `loadDocx` in `mcp/eversis-collections-mcp/src/docx/docx-io.ts` — any read failure, including a missing path, is rethrown as `Not a file: ${abs}`.
- `validateDocxFile` in `mcp/eversis-collections-mcp/src/docx/validate.ts` — same `path.resolve`.
- `backup_docx` and the optional `output_md_path` / `backup_dir` arguments in `mcp/eversis-collections-mcp/src/docx/tools.ts` — same `path.resolve`.

Tools that load through `loadDocx`: `generate_summary_map`, `read_chapter`, `update_chapter`, `upload_to_sharepoint`, `append_chapter`, `list_section_elements`, `inspect_document`, `update_table_cell`. `validate_docx` and `backup_docx` resolve paths themselves. A relative `docx_path` of `.playwright-mcp/backups/file.docx` therefore becomes `/app/.playwright-mcp/backups/file.docx`, which matches the ticket. The file, if it was copied into the consumer repo, is on the `/workspace` mount, not under `/app`.

A host absolute path (`/Users/...`) is not rewritten. `~/Downloads` is outside both mounts, so it stays invisible even after relative paths are fixed. A file inside the consumer project is visible at `/workspace/<project-relative-path>` today, if the caller already knows to pass that container path.

Public docs (`website/docs/reference/integrations/eversis-collections.md`, `website/docs/getting-started/mcp-setup.md`) explain `/repo` and `/workspace` for domain context. They do not say what `docx_path` is resolved against. The BA Docs skills (`.ai/skills/eversis-ba-docs-planner/SKILL.md`, `.ai/skills/eversis-ba-docs-writer/SKILL.md`) show `docx_path: /path/to/file.docx` and do not mention `/workspace` or a project-relative path.

Unit tests call `loadDocx` with an absolute temp path (`mcp/eversis-collections-mcp/tests/chapters.test.ts`). There is no test that a relative docx path resolves against the consumer workspace.

Quality commands for this area: `npm run mcp:build`, `npm run mcp:test`. Skill and website doc edits also need `npm run sync:adapters:check` when generated adapter copies change, and `npm run website:build` when the public docs page changes.

## Gap Analysis

### Question 1
#### Should a relative `docx_path` resolve against the consumer project (`/workspace`), using the same root as domain-context tools?
Yes. That is the mount that already contains the consumer repo. `path.resolve` against `/app` is why `.playwright-mcp/backups/...` becomes `/app/.playwright-mcp/...` in the ticket. Absolute container paths (`/workspace/...`, `/repo/...`) stay unchanged. Host absolute paths (`/Users/...`) stay unresolved and still fail, and the error should keep showing the path that was actually opened.

Confirmed by the user: `Q1. ok;`

### Question 2
#### Is reading a file outside the consumer repo (for example `~/Downloads`) in scope?
No. The acceptance criteria ask for one documented place a session can put a file, not for a mount of the host home directory or a new ingest tool. The session copies the `.docx` into the consumer project and passes a project-relative path (the existing `.playwright-mcp/backups/` habit remains valid once it resolves under `/workspace`). An upload tool or an extra volume is out of scope.

Confirmed by the user: `Q2. OK;`

### Question 3
#### What proves the path contract?
A unit test that a relative `docx_path` is opened under the workspace root rather than `process.cwd()`, covering load, validate, and backup (including optional `backup_dir` and `output_md_path`). The public MCP page and both BA Docs skills state the contract: project-relative paths, or an absolute path inside the container under `/workspace`. A Docker round-trip is not required for the gate if that unit test locks the resolution.

Confirmed by the user: `Q3. OK;`
