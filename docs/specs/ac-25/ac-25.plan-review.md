## WARNINGS

### W1: Planner template still models a host-like absolute `docx_path`

`.ai/skills/eversis-ba-docs-planner/SKILL.md` currently shows `docx_path: /path/to/file.docx`. That shape matches the ticket’s failing absolute-path attempts. Task 2.1 Description asks for project-relative / `/workspace` examples, but Definition of Done only requires the phrases `project-relative`, `/workspace`, and `.playwright-mcp/backups/` — an implementor can satisfy DoD without replacing the template line. **Action:** Add a DoD checkbox that the output-format example is project-relative or `/workspace/...`, not `/path/to/...` or `/Users/...`.

### W2: Tests never prove the production default root

Proposed Solution and Task 1.3 correctly inject a workspace root that is not cwd. That does not assert that one-arg `loadDocx` / `validateDocxFile` / backup default to `resolveWorkspaceRoot()`. A wiring miss would still pass the new suite. **Action:** Add one test (or DoD item) that omits the injected root and stubs/spies `resolveWorkspaceRoot` (or env + install-selection layout) so the default path is exercised.

### W3: DoD omits the `CONSUMER_PROJECT_ROOT` / install-selection prerequisite

Technical Context correctly notes that without install-selection on the consumer mount, `resolveWorkspaceRoot()` falls back to cwd `/app` and relative paths still fail. Task 2.1 Description says to point at `CONSUMER_PROJECT_ROOT`; DoD does not require that name (or install-selection). Agents can still hit “Not a file” after trial-and-error. **Action:** Require the skills (and preferably the Word-tools section) to name `CONSUMER_PROJECT_ROOT` and that `/workspace` is only treated as the project when install-selection is present — same rule as domain context.

### W4: Backup helper extraction target is unspecified

Task 1.2 requires extracting backup so tools and tests share one function, but Files only lists `tools.ts` / `paths.ts` / `docx-io.ts` without saying where the helper lands. **Action:** Name the module (e.g. export `backupDocx` from `docx-io.ts` or `paths.ts`) so Phase 1 does not churn on file placement.

## SUGGESTIONS

### S1: Optional path note on MCP tool descriptions

Research only requires a discoverable contract before pre-flight; skills + the public Word section meet that. Adding one sentence to `inspect_document` / `backup_docx` / `generate_summary_map` `description` strings would reduce reliance on skill load order. Out of scope unless cheap.

### S2: Clarify `output_md_path` test depth

Task 1.3 DoD says a relative `output_md_path` resolves under the workspace root. Prefer asserting through the same helper `generate_summary_map` will call (or a tiny exported resolve+default helper), not only a bare `resolveDocxPath` string check, so the write-side path cannot stay on `path.resolve`.
