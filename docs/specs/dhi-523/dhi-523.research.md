**User story:** As a framework architect, I want a written adapter mapping specification so that every core rule knows how it transforms into each tool's native format.

## Business Impact

Unblocks **Work Stream 2**: without this spec, Cursor (DHI-524), Claude Code (DHI-526), OpenCode placeholder (DHI-525), and sync tooling (DHI-527) will diverge. Core SSOT → tool packaging is a prerequisite for installer (5.x), isolation (3.x), and the EOG pilot (Cursor frontend / Claude backend).

## Acceptance Criteria (from Jira)

1. Mapping spec is complete: field mapping for **Cursor** (`globs`, `description`, `alwaysApply`), **Claude Code** (`scope`, `commands`), and **OpenCode** (manifest placeholder)
2. When a core rule is processed through the spec, **output structure is unambiguous** for Story 2.2–2.4 implementers
3. Spec states **which core artifacts** each adapter emits (rules only vs rules + prompts + skills summaries)
4. Inherited SDD AC (spec folder, research → plan → implement → review → Fine)

## Gap Analysis

### Question 1
#### Where should the **committed** mapping specification live (`docs/specs/dhi-*/` is local-only)?
**Options:**  
**A)** `docs/architecture/adapter-mapping.md` (or equivalent committed docs)  
**B)** `adapters/MAPPING.md` (+ `adapters/` tree)  
**C)** Expand `.ai/README.md` only  
**D)** Spec only under local `docs/specs/dhi-523/` + short pointer in `.ai/README.md` / root README  

**Answer (approved 2026-08-05):** **A** — `docs/architecture/adapter-mapping.md` (+ short pointer in `.ai/README.md`).

### Question 2
#### Does DHI-523 deliver **document only**, or also **directory stubs** `adapters/{cursor,claude-code,opencode}/` without generators?
**Options:**  
**A)** Document only (dirs/code = 2.2+)  
**B)** Document + empty stubs + per-adapter README  

**Answer (approved 2026-08-05):** **A** — document only; `adapters/` dirs in DHI-524+.

### Question 3
#### Beyond `.cursor/rules/*.mdc`, what does the Cursor adapter emit in the MVP described by this spec?
**Options:**  
**A)** Rules only; prompts/skills/commands outside MVP matrix  
**B)** Rules + slash commands; skills via MCP; prompts not copied  
**C)** Full mirror `.cursor/{rules,prompts,skills,commands}`  

**Answer (approved 2026-08-05):** **A** — MVP = `.mdc` rules only.

### Question 4
#### What Claude Code output shape is “unambiguous” for DHI-526?
**Options:**  
**A)** Single `CLAUDE.md` (sections = domain/orchestration); skills/prompts outside adapter (MCP / AGENTS)  
**B)** `CLAUDE.md` + native Claude commands/skills if supported  
**C)** Minimal `CLAUDE.md` (orchestration + pointer to `.ai/`) without full inlining  

**Answer (approved 2026-08-05):** **A** — single `CLAUDE.md` with sections; skills/prompts outside adapter.

### Question 5
#### Where do `description` / `globs` / `alwaysApply` come from (core has no front matter)?
**Options:**  
**A)** Sidecar next to each rule (e.g. `agent-core.cursor.yml`)  
**B)** Central map in adapter layer (`adapters/cursor/rule-map.yaml`)  
**C)** Path/folder convention (orchestration→alwaysApply; frontend→glob set; roles→attach-only) + small exception table  

**Answer (approved 2026-08-05):** **B** — central adapter map (e.g. `adapters/cursor/rule-map.yaml`); DHI-523 documents the map contract only (no YAML file yet).

### Question 6
#### How deep should the OpenCode placeholder be in this story?
**Options:**  
**A)** Minimal manifest (adapter id, `placeholder` status, TBD outputs) sufficient for AC  
**B)** Richer field sketch aligned to current public OpenCode docs  

**Answer (approved 2026-08-05):** **B** — richer sketch aligned to public OpenCode conventions (verify docs during plan/implement).
