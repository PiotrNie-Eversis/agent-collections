**User story:** Jako maintainer frameworka chcę mieć placeholder adaptera OpenCode, żeby przyszła integracja nie wymagała przepisywania core.

## Wpływ biznesowy

Domknięcie trzeciego „slotu” Work Stream 2 (Cursor / Claude / OpenCode): wizard (5.6) i dokumentacja mogą wskazać OpenCode jako **`placeholder`**, a nie wymyślać kontraktu ad hoc. Chroni inwariant **core SSOT** — zmiany formatu OpenCode żyją w warstwie adaptera. Nie odblokowuje pilota EOG (Cursor+Claude), ale zmniejsza ryzyko driftu i spełnia założenie #3 extracted-tasks (OpenCode tylko stub).

## Kryteria akceptacji (z Jira)

1. **Manifest:** GIVEN architektura adapterów WHEN wsparcie OpenCode jest stubowane THEN istnieje szablon manifestu/config dokumentujący oczekiwane pola i haki mapowania na core
2. **Stabilność core:** GIVEN placeholder WHEN przeglądany THEN jest jasne, że core pozostaje niezmieniony gdy ewoluuje format OpenCode
3. **Izolacja indeksów:** GIVEN struktura repo WHEN sprawdzona THEN pliki adaptera OpenCode są wykluczone z indeksów innych agentów (patrz Story 3.2 / [DHI-529](https://eversis.atlassian.net/browse/DHI-529))
4. Dziedziczone AC SDD (folder spec, research → plan → implement → review → Fine)

## Gap Analysis

### Pytanie 1
#### Gdzie ma żyć **committed** `opencode.json` w tej story?
**Opcje:**  
**A)** Tylko `adapters/opencode/opencode.json` (szablon / kanoniczny stub w warstwie adaptera); root **bez** pliku — konsument kopiuje przy install (5.x)  
**B)** Root `opencode.json` **oraz** kopia/źródło w `adapters/opencode/` (repo frameworka demonstruje żywy config)  
**C)** Tylko root `opencode.json`; katalog `adapters/opencode/` ma wyłącznie README + status (bez JSON)

**Wyjaśnienie:** Mapping §6 mówi „Generated or hand-maintained placeholder target (DHI-525)” i pokazuje JSON jak dla projektu. Inventory / DHI-515 wskazują `adapters/opencode/` jako *manifest stub*. A trzyma jasną granicę „adapter layer owns packaging”; B ułatwia lokalny smoke test OpenCode w tym repo i jest bliższe Cursor (który emituje in-place do `.cursor/`). C łamie konwencję siblingów `adapters/{cursor,opencode}/`.  
**Rekomendacja:** **B** jeśli chcemy dowodu „działa w framework repo”; **A** jeśli priorytetem jest czystość (installer skopiuje później). Preferuję **B** przy małym koszcie.

**Odpowiedź (zatwierdzona 2026-08-06):** **B**

#### Czy DHI-525 zawiera **jakikolwiek generator / skrypt**, czy wyłącznie pliki statyczne?
**Opcje:**

**B)** Minimalny skrypt kopiujący template → root (lub walidujący JSON vs schema)  
**C)** Pełniejszy generator mapujący rule-map → instructions (zbliżone do 524/527)

**Wyjaśnienie:** BRD / Jira: implementacja odroczona. C to scope creep w stronę DHI-527 i pełnego adaptera. B dodaje tooling bez wymogu AC. A spełnia AC #1–#2 przy najmniejszym ryzyku.  
**Rekomendacja:** **A**.

**Odpowiedź (zatwierdzona 2026-08-06):** **A**

### Pytanie 3
#### Jak spełnić **AC #3** (wykluczenie z indeksów innych agentów), skoro Story 3.2 (DHI-529) jest jeszcze To Do?
**Opcje:**  
**A)** **Defer** pełnej triady do DHI-529; w 525: udokumentować w README listę ścieżek do wykluczenia + checklistę dla 3.2; AC #3 oznaczyć jako „hooks documented; enforcement in 529” (wymaga świadomej akceptacji partial AC)  
**B)** **Minimal now:** dodać do `.cursorignore` (i ewentualnie stub `.claudeignore`) wykluczenia ścieżek OpenCode-only (np. `adapters/opencode/`, root `opencode.json` jeśli nie ma być czytany przez Cursor) — bez pełnej synchronizowanej triady  
**C)** Dostarczyć w 525 szkielety trzech ignore z **tylko** sekcją OpenCode (częściowy overlap z 529)

**Wyjaśnienie:** AC Jira wprost mówi „see Story 3.2”. Dosłowne pełne spełnienie bez 529 jest niemożliwe (brak `.claudeignore` / `.opencodeignore` i strategii 3.1). A jest uczciwe względem zależności, ale pozostawia dziurę w AC. B daje namacalny krok izolacji Cursor↔OpenCode bez kradzieży zakresu 529. C ryzykuje konflikt z przyszłą strategią 528/529.  
**Rekomendacja:** **B** (minimalne wpisy w `.cursorignore` + dokumentacja ścieżek dla 529) **albo** **A** jeśli EM woli twarde defer i notatkę w planie „AC #3 partial / tracked in 529”. Preferuję **B**.

**Odpowiedź (zatwierdzona 2026-08-06):** **B**

### Pytanie 4
#### Format pliku config: **JSON** czy **JSONC** (komentarze)?
**Opcje:**  
**A)** Czysty JSON (zgodny ze szkicem mapping §6.1)  
**B)** JSONC z nagłówkowym komentarzem „PLACEHOLDER — do not treat as shipped adapter; core SSOT is `.ai/`”  
**C)** Oba: `opencode.json` (czysty) + `opencode.jsonc.example` z komentarzami

**Wyjaśnienie:** OpenCode docs wspierają JSONC. Komentarz wzmacnia AC #2 (jasność dla reviewerów). Czysty JSON jest prostszy w walidacji/`$schema`. B łączy czytelność z jednym plikiem.  
**Rekomendacja:** **B** jeśli OpenCode w projekcie toleruje JSONC w ścieżce `opencode.json` / `opencode.jsonc`; inaczej **A** + mocny README. Sprawdzić w planie nazwę pliku (`opencode.json` vs `opencode.jsonc`).

**Odpowiedź (zatwierdzona 2026-08-06):** **B**

**Rekomendacja:** **A** (zgodność ze spec); ewentualnie nota w README „README.md may be loaded; refine in future shipped adapter”.
