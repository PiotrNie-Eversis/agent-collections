# Pi adapter

Generates the [Pi coding agent](https://pi.dev/)'s project surfaces under `.pi/` from Agent Collections core (AC-14): a small always-on core in `.pi/APPEND_SYSTEM.md`, role rules as `.pi/skills/eversis-rule-*/SKILL.md`, slash commands in `.pi/prompts/eversis-*.md`, a process-rules extension that adds the rules on demand, a context-budget extension, and a one-time `.pi/settings.json` seed. `.pi/skills/eversis-*/` (framework skills) and `.pi/mcp.json` are written by the installer, not by this generator (see "Generated skills" and "MCP" below). Mapping contract: [`docs/architecture/adapter-mapping.md`](../../docs/architecture/adapter-mapping.md) §6A.

Pi is **opt-in**: `adapters/sync.mjs` keeps its default `cursor,claude`, and this repository does not commit a `.pi/` tree.

## Run (from repository root)

Through the sync CLI (Pi runs last, after Cursor / Claude):

```bash
node adapters/sync.mjs --agents cursor,claude,pi --out /path/to/project
node adapters/sync.mjs --check --agents cursor,claude,pi --out /path/to/project
```

Pi only:

```bash
node adapters/pi/generate.mjs --out /path/to/project
node adapters/pi/generate.mjs --out /path/to/project --framework-prefix vendor/agent-collections
node adapters/pi/generate.mjs --out /path/to/project --check
```

- `--out <dir>` — target project root (default: this repository).
- `--framework-prefix <path>` — prepends the vendored framework path to SSOT pointers (`> SSOT: …` lines), same as the Claude generator. Absolute paths and `..` segments are rejected.
- `--check` — writes nothing; exits 1 and lists every `missing:`, `drift:` or `orphan:` file. `node adapters/sync.mjs --check --agents …,pi` delegates to this check against the real target.

The installer runs the generator for you with `--agents=pi` (see "Installer" below). Re-run after core, map or asset changes. **Do not hand-edit** generated files — they are overwritten on the next run.

## Markers and cleanup

Every generated file carries `GENERATED by adapters/pi/generate.mjs — do not edit; re-run the generator` (an HTML comment in Markdown, a `//` comment in the `.ts` extension). Orphan cleanup removes only marker-bearing `eversis-*.md` prompts and `eversis-rule-*` skills that the SSOT no longer produces. Hand-made files under `.pi/` that the generator does not target are never touched.

If a path the generator writes (`.pi/APPEND_SYSTEM.md`, `.pi/prompts/eversis-<id>.md`, `.pi/skills/eversis-rule-*/SKILL.md`, `.pi/extensions/eversis-process-rules.ts`, `.pi/extensions/eversis-context-budget.ts`) already holds a hand-made regular file without the marker, a write run first copies it byte-identical to `<name>.pre-agent-collections.bak` in the same folder and prints `warning: backed up hand-made <path> to <backup path>` to stderr, then writes the generated file. If that backup already exists with different content, the copy goes to `<name>.pre-agent-collections.<YYYYMMDDTHHMMSS>.bak` instead (an identical backup is reused, so an older backup is never overwritten). Marker-bearing files and symlinks are replaced without a backup. `--check` only reports such a file as `drift:` and writes nothing. `.pi/settings.json` is seeded only and never overwritten. Same convention as the Claude adapter's `CLAUDE.md.pre-agent-collections.bak`.

## Pi-safe prompt bodies

- **Front matter** values are written as JSON-quoted strings. Pi's YAML parser rejects unquoted values containing `": "` and would silently drop those prompts.
- **`$` neutralisation:** Pi substitutes `$<digit>`, `$@`, `$ARGUMENTS` and `${…}` anywhere in a prompt and has no escape syntax. In SSOT body text the generator replaces each `$` that starts one of those patterns with `＄` (U+FF04, fullwidth dollar sign), so dollar amounts and shell snippets stay readable. Only the final `**User input for this run:** $ARGUMENTS` line stays live. The SSOT pointer line is left as-is, so a local-mode `${AGENT_COLLECTIONS_HOME}` pointer stays readable (Pi does not substitute that token).

## Project-stack overlay

When the target has `.cursor/rules/eversis-project-stack.mdc` **and** it differs from the framework template `templates/eversis-project-stack.example.mdc` **and** it carries none of the template placeholder markers (`<!-- TODO`, `replace with your product stack`), its body (front matter stripped) is appended to `.pi/APPEND_SYSTEM.md` as the consumer overlay. An absent file or an unedited seed is skipped with a one-line hint, so template placeholder text never becomes always-on. Customise that file, then re-run the sync to pick it up. Nothing else from the consumer is appended.

## Process rules on demand

Pi used to carry the process rules on every request, including a one-line question. Now a session without a command costs close to plain Pi, and a command still gets the full process (AC-134).

**Always on, in every Pi session:** `.pi/APPEND_SYSTEM.md`, a small core of about 1,500 characters. It holds the hard limits, the line that runs lint, typecheck and tests after substantive code changes, one hard line that ticket work starts with `/eversis-implement <ticket>`, a pointer to the commands, and the project-stack overlay when you have one.

**Added only when active:** `.pi/extensions/eversis-process-rules.ts` adds five rule skills to the system prompt as one section, and keeps every skill in the skill listing: `eversis-rule-agent-core`, `eversis-rule-testing-and-terminal`, `eversis-rule-accessibility`, `eversis-rule-engineering-manager`, `eversis-rule-spec-driven-development`. The text is read at runtime from those skills' `SKILL.md`, so it has one source. When the rules are not active, the extension removes `eversis-*` entries from the listing. Your own skills stay listed, and `/skill:<name>` still works for every skill.

The rules turn on in two ways:

- **An `eversis-*` command.** Any of the 28 prompt commands turns them on from its first request, for the rest of that session. The state survives `--continue`, `/reload` and compaction. A new session starts without it. A command sent while the agent is busy starts the rules with the next run, and the notice says so.
- **An active plan.** When Pi edits or writes a `docs/specs/**/*.plan.md` file and the tool succeeds, the extension saves that path in `.pi/eversis-state/active-plan.json`. A new session starts with the rules on if that plan still has an open checkbox. The running session does not change, and a plan Pi never edited does not count. A plan with no open checkbox clears the pointer, and so does a session started where the plan file is absent, such as on another git branch; the rules then stay off until a command or a new plan edit. The notice names the plan and the file; delete that file if the work is abandoned.

`.pi/eversis-state/` ignores itself with its own `.gitignore`, so your `.gitignore` does not change. The extension writes only in that folder, and makes no network or shell calls. It refuses symlinks planted in that path, but the check is not atomic against another process running as the same user at the same moment. Pi deselect removes the folder.

**Exception to the Delivery Standard:** in Pi, the process runs only after a command or with an active plan. A plain request such as "implement AC-123" gets the hard limits and the quality checks, but not the research, plan and review gates. The only guard is the core's line telling the model to ask for `/eversis-implement` first, and a model can ignore it. Cursor and Claude Code keep their rules always on, so this applies to Pi alone. Start ticket work with the command.

**Domain knowledge:** `eversis-add-domain-knowledge` is a skill, not a prompt, so it is not one of the 28 commands, and asking in plain words may no longer find it because it is hidden from the listing. Run it with the exact command `/skill:eversis-add-domain-knowledge`. It does not turn the process rules on.

### Measured difference

System prompt as sent to the model, recorded by a stub model on Pi 1.5.0. Tokens are estimated as characters / 4.

| Request | Before AC-134 | After AC-134 |
|---------|---:|---:|
| Session without a command | 42,902 chars (~10.7k tokens) | 4,556 chars (~1.1k tokens) |
| First request of `/eversis-implement` | 42,902 chars (~10.7k tokens) | 57,908 chars (~14.5k tokens) |

A session without a command is 89% smaller. A command run is 35% larger than before: it now carries the Engineering Manager and spec-driven rules as text, on top of the full listing.

Setup: the 50 framework skills, one consumer skill, no stack overlay, no `AGENTS.md`, and a project path of 90 characters. The listing holds each skill's absolute path, so a longer path costs more: research recorded 45,996 chars for the same "before" at a longer temp path. Your context file and overlay add to all of these numbers.

`adapters/pi/process-rules.integration.mjs` proves this on real Pi with that stub model, and fails if the section stops reaching the request. It skips when `pi` is not on PATH, and CI runs it on the pinned and latest Pi:

```bash
node --test adapters/pi/process-rules.integration.mjs
```

## Context budget

Pi can compact a long session, but Agent Collections wants compaction earlier, while the plan and its gates are still in view. The extension `.pi/extensions/eversis-context-budget.ts` compacts the session **once** when context use crosses a budget:

- **Budget:** `EVERSIS_CONTEXT_BUDGET_PERCENT` (integer 1–95); default **50**. Invalid values fall back to 50.
- **When:** on `turn_end`, when `ctx.getContextUsage().percent` reaches the budget and the previous known reading was below it or unknown (first reading, or right after a compaction). Readings that stay above the budget do not fire again. After a compaction the extension triggered, the next known reading only sets a new baseline and never fires, even when it is still over budget (a small context window whose retained context stays above the budget does not loop compaction + continuation every turn); the next compaction needs a fresh below → at/over crossing. An unknown → over-budget first reading still fires once (for example a resumed session that is already over budget).
- **Summary instructions** keep the active `docs/specs/**/*.plan.md` path (and research path), the current phase / task and its DoD state, the latest `CHECKPOINT:` / `RESUMED:` rows, any open human gate (never recorded as approved unless the human approved it), and the next step.
- **Continuation:** Pi's compaction aborts the running turn and does not resume it. When the crossing turn was **mid-task** (it had tool results), the extension sends **one** automatic message after compaction: resume the current plan task from the summary, re-read the plan file first, do not restart finished tasks, do not pass an open human gate, and — if there is no active plan — continue the interrupted task from the compaction summary. The message states it is automatic and not an approval of any gate. When the crossing turn was a **final turn** (no tool results: the agent finished, asked a question, or stopped at a gate), it compacts and shows a notice only — no unrequested run starts and nothing can be read as gate approval.

This is **Pi-only**. Cursor and Claude Code have no window-fill trigger: rule 14 of `eversis-orchestrating-implementation` (no window-fill trigger, AC-2 decision) is unchanged.

The extension has no network access, file writes, or shell calls, and only an `import type` from `@earendil-works/pi-coding-agent` (no runtime dependency).

## Review in Pi

The Implement workflow wants code review in a context separate from the one that wrote the code: self-review is not verification (`eversis-orchestrating-implementation`, step 8). Cursor and Claude Code delegate review to a sub-agent. **Pi has no sub-agents**, so when `/eversis-implement` reaches the Review stage, the same model in the same context reviews its own change. That review is weaker and is not independent.

The generator makes this visible. Rules flagged `review_context_note: true` in [`rule-map.yaml`](./rule-map.yaml) (`eversis-engineering-manager`, `eversis-code-reviewer`) get a Pi host note at the top of their role skill. With it, every review result in Pi starts with one line:

- `Review context: same session as implementation (not independent)` — the session that implemented or edited the change also reviewed it;
- `Review context: fresh session (independent)` — a new session that did not implement it.

After a same-session review the result ends with the next step, and at Fine the QA comment draft repeats the `Review context:` line under **Automation & Technical Notes**.

**Get an independent review today:**

1. Finish the Implement run (or stop it at Review).
2. Start a new Pi session in the project root (`pi`, or `/new` in an open session) — a clean context.
3. Run `/eversis-review AC-123`. With only the key, the reviewer looks for `docs/specs/ac-123/` first, then the single `docs/specs/ac-123-<topic>/` folder, and asks if more than one matches. To skip the lookup, add the path: `/eversis-review AC-123 docs/specs/ac-123-topic/`.
4. The result starts with `Review context: fresh session (independent)`.

Do not use `/fork`, `/clone` or `/tree` for this: they keep the earlier conversation, so the review would not be independent. A review that runs automatically in a separate Pi session is planned (AC-136); until then, the fresh-session review is the recommended step for any change that matters. The note is Pi-only: Cursor and Claude Code output is unchanged.

## Generated skills

`.pi/skills/eversis-*/` is **not generated** by this script — the installer's shared `_link_agent_skills` (`scripts/lib/setup-agent-collections/link-framework.sh`) links (symlink) or copies one entry per `.ai/skills/eversis-*/` directory, the same contract as `.claude/skills/` and `.cursor/skills/`. Its stale-prune skips `eversis-rule-*` entries, which belong to this generator.

## MCP

The installer writes the `eversis-collections` server into `.pi/mcp.json` (`mcpServers` format, no `inputs`). Pi does not expand `${VAR}` in `command` / `args` and starts servers in the session directory, so the entry is a `bash -c` locator that walks up from `$PWD` to the nearest directory containing `.pi/` (the project root):

- **Vendored** (copy / submodule): execs `scripts/run-eversis-collections-mcp.sh` (copied for Pi as for Claude Code).
- **Local:** `docker compose -f "${AGENT_COLLECTIONS_HOME:-<framework path>}/docker-compose.yml" run --rm -T eversis-collections` with `CONSUMER_PROJECT_ROOT` set to the project root. The `${…}` default is evaluated by bash, not by Pi. When the framework path contains a character that would break that double-quoted default (`}`, `"`, `$`, a backtick or `\`), the script first assigns the path single-quoted to `ac_home='…'` and the default becomes `$ac_home`, so bash still receives the exact path.

Other selected catalog servers are copied as-is; the merge fails (as a Pi failure) if one still contains `${workspaceFolder}`, `${env:…}` or `CLAUDE_PROJECT_DIR` in `command` / `args`. Check the result with `pi mcp list`.

## Installer

- **Select:** `--agents=pi` (alone or with `cursor` / `claude`), the `pi — Pi coding agent (pi.dev)` checkbox, or numbered menu `6) Pi only` / `7) Cursor + Claude + Pi`.
- **Isolated stage:** generation, the skills mirror, deselect pruning and the `.pi/mcp.json` merge run as one Pi stage. A Pi failure prints a dedicated `pi` error with its cause, keeps the other agents' output, leaves `pi` out of `.agent-collections/install-selection.json`, shows `agent-collections setup completed with failures (pi)`, and exits 1 at the end. A Pi-only run exits 1 right after the failed stage.
- **Missing `pi` CLI:** summary warning only (`npm i -g @earendil-works/pi-coding-agent`); `.pi/` is still generated.
- **Deselect** (re-run with `--agents` without `pi`): removes framework-generated `.pi/APPEND_SYSTEM.md`, `.pi/prompts/eversis-*.md`, `.pi/skills/eversis-*` (framework skills and `eversis-rule-*` role skills), `.pi/extensions/eversis-context-budget.ts`, `.pi/extensions/eversis-process-rules.ts` and `.pi/eversis-state/`. `.pi/settings.json` and `.pi/mcp.json` stay.
- **Upgrade:** `--upgrade` keeps `pi` selected when `.pi/APPEND_SYSTEM.md` carries the generator marker.

## Consumer project notes

- **Project trust:** Pi loads `.pi/` only after you grant project trust. Start `pi` in the project root and accept it. `AGENTS.md` / `CLAUDE.md` load without trust; nothing under `.pi/` does.
- **`/reload`:** after a re-sync, run `/reload` in an open Pi session to pick up regenerated files.
- **`APPEND_SYSTEM.md` replaces the user-level one:** a trusted project `.pi/APPEND_SYSTEM.md` replaces (does not combine with) `~/.pi/agent/APPEND_SYSTEM.md`. Move personal additions into the project overlay or a Pi skill.
- **Review the extensions before trusting:** once trusted, `.pi/extensions/eversis-context-budget.ts` and `.pi/extensions/eversis-process-rules.ts` run inside Pi with your user privileges. They are short and dependency-free — read them first.
- **TypeScript / ESLint:** each extension's `import type` from `@earendil-works/pi-coding-agent` does not resolve in a project that does not install Pi locally. Exclude `.pi/extensions/` from the consumer's `tsconfig` / ESLint config if their checks cover it.
- **Keep a root `AGENTS.md`:** Pi reads `AGENTS.md` or `CLAUDE.md` as its context file and prefers `AGENTS.md`. A `claude,pi` project without a root `AGENTS.md` loads the full generated `CLAUDE.md` (all seven rules) on every request, so the small core does not hold and sessions without a command stay expensive.
- **Not in AC-14:** Pi ignore files / heavy-file exclusion (AC-113), subscription sign-in and model settings (AC-111), further token-economy trimming (AC-112), isolated workspace / sandbox (AC-114).

## Load check

A new Pi release can stop loading part of the `.pi/` tree without an error you would notice (for example, it drops a prompt whose front matter it cannot parse). `scripts/pi-load-check.mjs` (AC-138) catches that. It uses the `pi` on your PATH:

1. Installs the framework for Pi into a temp project (`setup-agent-collections.sh --agents=pi`, non-interactive).
2. Starts `pi --mode rpc` in that project and asks for its command list (`get_commands`).
3. Runs Pi's own MCP config loader on `.pi/mcp.json`.

It fails (exit 1) when Pi exits non-zero or times out, writes to stderr (an extension that does not load), is missing a generated prompt or skill, reports an MCP `config:` error, or its MCP loader reports errors. Every problem is printed and named, for example the prompt Pi dropped. The report always starts with `Pi <version> (<label>)` and the prompt / skill counts. Exit 2 means a usage error, no `pi` on PATH, or an installer failure. A failed MCP server connection is printed as `info:` only.

```bash
npm run pi:load-check
node scripts/pi-load-check.mjs --project /path/to/project   # check an existing project, skip the install
```

Other options: `--label <text>` (printed in the report; default `local`), `--settle-ms <n>` (wait for MCP notices after the response; default 5000), `--timeout-ms <n>` (default 60000), `--keep` (keep the temp dir and print its path). Tests: `node --test scripts/pi-load-check.test.mjs` (the integration tests run only when `pi` is on PATH).

- **Isolated, no credentials:** Pi runs with a temp `HOME` and only `PATH`, `HOME`, `TERM` and `NODE_NO_WARNINGS` in its environment, so no provider API key reaches it and no model is called. The check also compares your real `~/.pi/agent` before and after the run (`sessions/` and `install/` excluded) and fails if anything there changed.
- **Stub `docker` for the installer:** the installer needs `docker` for the MCP image step. The check puts a stub `docker` first on the installer's PATH that reports the image as already built, so no image is built and no real Docker is needed. `.pi/mcp.json` is written as usual.
- **Always-failing `docker` for Pi:** Pi gets a different stub `docker` that always exits 1, so no MCP container ever starts and the MCP server fails to connect the same way in CI and on a machine with Docker.
- **Other Pi sessions:** the home check can also report changes made by another Pi session that runs on the same machine at the same time. Close it, or re-run.

GitLab CI runs the check on the pinned Pi version for framework changes and on the latest Pi release weekly. Jobs, schedule setup and the pin-bump rule: [`scripts/README.md`](../../scripts/README.md) ("Pi load check in CI").

## Requirements

- Node.js 18+ (stdlib only; no npm install). The `node:test` suites (`node --test 'adapters/pi/*.test.mjs'`) import the `.ts` extension and need Node ≥ 22.18 (dev-only).
- Pi coding agent (`npm i -g @earendil-works/pi-coding-agent`) to use the generated tree. **Minimum Pi 1.5.0.** CI checks the pinned version (`PI_VERSION_PINNED`) and the latest release weekly (see "Load check").
- Run from the **repository root** (directory that contains `.ai/` and `adapters/`).
